# Architecture

## Modules

```
app ──────────────┬──> overlay ──┬──> core:ocr ──> core:common
                  │              ├──> core:photos ──> core:ocr
                  │              ├──> core:anki ─> core:common
                  │              ├──> core:translate ──> core:common
                  │              └──> dictionary:api ──> core:common
                  ├──> dictionary:engine-hoshidicts ──> dictionary:api   (hoshidicts, QuickJS-ng)
                  └──> dictionary:render-yomitan (assets only)
```

| Module | Contents |
|---|---|
| `app` | Application (Hilt, WorkManager factory), Compose screens: home with setup warnings, search, one Settings screen leading to bubble (with its hidden apps), text recognition (`recognition/`, with the OCR test), lookup, dictionaries, Anki, audio (`audio/`), popup, translation (`translate/`), appearance (theme, e-ink mode, language, popup font and CSS), backup and restore (`backup/`) with the Yomitan import as its last card (`yomitan/`), background work and About. The Languages screen, the first run and a language's download screen (`languages/`). The dialog about what the accessibility service reads and sends comes before its settings open until the user agrees (`home/AccessibilityDisclosure`). `ProcessTextActivity` for the text selection menu. |
| `overlay` | Accessibility service, bubble state machine (`OverlayController`), window screenshots, app text from the accessibility tree, the lookup page (`web/LookupPage`, `assets/popup/`), popup placement, crop editor, Anki buttons (`anki/PopupNotes`), page fonts and custom CSS (`fonts/`), Quick Settings tile (holding it opens the app through `BubbleTileSettingsActivity`), the optional keep-alive foreground service (`BubbleKeepAliveService`), the service's running state for the start screen (`OverlayServiceStatus`), whether the active language is ready to scan (`install/LanguageInstallation`), round flags for languages (`ui/Flags`). |
| `core:common` | `Language` and `LanguageSupport` (everything language-specific: lookup start, spelling variants, romaji, sentence rules, fonts, audio defaults), `MappedText`, the Simplified and Traditional Chinese character table, geometry, app settings, language profiles (`LanguageProfiles`: turned-on, active and starred languages), shared OkHttp client, local network address checks, log redaction. |
| `core:ocr` | `OcrEngine` with a cloud engine (hand-written protobuf) and the device (`DeviceOcr`: ML Kit, or an engine with downloaded models from `OcrModelStore`: Tesseract, PaddleOCR), `CompositeOcr` (draft, then final), `TextLayout` for hit testing. |
| `core:ocr-mnn` | MNN (submodule, CPU backend) and its JNI wrapper `MnnNetwork`, which runs the PaddleOCR models. |
| `core:photos` | The current photo and the photo history with their recognized text (`PhotoStore`: the image and a versioned binary snapshot of the text in no-backup storage, metadata in Room), EXIF orientation (`PhotoOrientation`), where the photo is drawn on the screen (`PhotoViewport`) and the source the bubble reads (`LookupSources`). |
| `core:anki` | AnkiDroid API wrapper behind `AnkiBackend`, note settings, field templates, sentence extraction, setup status, audio sources and playback. |
| `core:translate` | `SentenceTranslator` over the Bing, Google and Edge translators (`Translator`), the language table (generated by `scripts/translation/languages.py`), translation settings. |
| `dictionary:api` | `DictionaryEngine` interface and lookup models, registry (Room), import queue (WorkManager), bundled dictionaries, download catalog (formats 1 and 2), update check, `YomitanSorter`, Yomitan collection export converter, the files written next to a dictionary at import (tag notes, transcription tags, reading index), form-of tag names, the wordfreq frequency dictionary builder. |
| `dictionary:engine-hoshidicts` | `DictionaryEngine` on top of hoshidicts (C++, JNI); for languages other than Japanese, Yomitan's language code in QuickJS (bundles in `assets/yomitan-language`) and the form-of table. GPL-3.0. |
| `dictionary:render-yomitan` | JavaScript and CSS that render Yomitan structured content, images, furigana and pitch accent. GPL-3.0. |

The two GPL modules implement interfaces or asset contracts defined elsewhere, so they can be replaced without touching the rest.

## From the bubble to a dictionary entry

1. **Scan.** Pulling the bubble out of the dock (or tapping it) takes a screenshot of the app window under the overlays (`takeScreenshotOfWindow`, API 34+; older versions capture the display with the overlays hidden for a frame), so the popup is never recognized and the text under it is. With "Read app text", `AccessibilityText` reads the application windows' accessibility tree while the screen is captured, and OCR runs as well. Neither waits for the other: whichever is ready is shown, and app text takes precedence where both have text, with OCR adding only the lines app text lacks. "App text only" skips the screenshot and OCR (the screenshot is taken later only when a note asks for a picture). Nodes whose character boxes cannot be trusted are left to OCR: the same box for every character (a WebView reporting the node's bounds) and text fields whose first box sits at the field's corner (Compose fields, whose boxes include the padding). A combining mark typed apart (a stress or tone mark), which a text view gives an empty box, stays with its letter. A paragraph whose first strong letter is Arabic or Hebrew is read as right-to-left lines: a line ends where a character falls below the previous one or starts back to the right by half its width, unless it is of the other direction (a Latin run or a number inside the line).
2. **OCR.** `CompositeOcr` runs ML Kit on the device and the cloud engine in parallel. ML Kit first reads a band of the screen around the aim (`FocusBand`, again when the aim has moved out of it), then the whole screen; each result is shown as a draft until the cloud result replaces it. ML Kit's time grows with the amount of text, so the band is ready several times sooner than the whole screen. The model is loaded when the bubble starts and again when another model takes over (chosen in the settings, installed or deleted). The cloud engine gets a JPEG of at most 1500 px; its coordinates are normalized to the image and mapped back to the screen. A touch on the bubble opens the connection to the cloud host with a request that carries no screen content, unless the host was contacted in the last 30 s, so the first scan after a pause does not wait for the handshake; the scan's request waits up to 3 s for a connection being opened. `OcrOptions` can limit a scan to one engine or defer ML Kit's whole-screen pass until the cloud engine is 3 s late or fails (`deferWholeImage`). ML Kit's symbol boxes sometimes lag behind the glyphs by up to half a character; `SymbolLag` moves the inner boundaries of such words onto the gaps between glyphs when the pixels clearly show them. The cloud engine gives an Arabic line in reading order but a Hebrew or Persian one word by word from right to left on the screen, which reverses a run of Latin words, so in a right-to-left line a run of words without right-to-left letters that holds a Latin letter is put in the order of its boxes (`LensProtocol.leftToRightRuns`), and separators stay in their places. A line that comes in neither order (one mixing a number after a prefix with Latin words) is put in the order of its boxes' right edges, with a space where two boxes stand apart (`LensProtocol.inReadingOrder`).
3. **Hit test.** `TextLayout` splits every recognized word into characters (per-character boxes when the engine has them, otherwise even splits along the word's reading direction (a Latin word or a number in a right-to-left line runs left to right), in which a mark written above or below its letter, as Thai vowels and tone marks and Arabic harakat are, takes no share of its own, nor does a Khmer consonant written below another) and finds the character under the aim point. The text from that character to the end of its paragraph, up to the scan length (16 characters by default, 24 in Georgian, Armenian, Arabic, Persian and Hebrew: `LanguageSupport.defaultScanLength`), is the lookup text; in a language written with spaces it starts at the beginning of the word under the aim, which includes combining marks, the zero-width joiners and the punctuation a language writes inside words (`SpacedLanguageSupport.wordMarks`: the Armenian marks on a stressed vowel); between two letters, the apostrophe and the hyphen join them into one word, and in Hebrew the maqaf, the geresh, the gershayim and the ASCII quote written for it as well (`SpacedLanguageSupport.wordConnectors`). The word after an elided one (French l', Italian dell') or after a Romanian pronoun or preposition joined to it with a hyphen (s-a, într-o) starts anew (`SpacedLanguageSupport.elisions`, `hyphenElisions`). A language written without spaces between words (Thai, Khmer) finds the word with Android's ICU word segmentation (`SegmentedLanguageSupport`, behind `WordSegmenter`), which reads up to 32 characters after the aim as well to tell which word the aimed letter is in; a word starts at a segment boundary that begins a letter cluster (not before a vowel sign or tone mark, not after a leading vowel such as เ). Words, and the lines of a paragraph, are joined by each word's separator (none in Japanese), so a phrase broken across lines is still found. Cloud recognition gives no separator after a word hyphenated at a line end; `withHyphenBreaks` puts the language's separator there, so the lookup sees the break. `ReadingOrder` puts paragraphs into reading order first: vertical columns right to left, and a column that runs to the bottom of its text joined with the column that goes on from it, so a word broken at a line or column end is read as a whole.
4. **Lookup.** `DictionaryLookup` loads the enabled dictionaries into the engine on first use. hoshidicts deinflects every prefix of the lookup text, groups results by expression and reading, and sorts them. In Japanese, form-of entries (a glossary item `["lemma", ["tag", …]]`, as in Wiktionary's rows of inflected forms and spellings) are then followed one step, as Yomitan does: the items leave the definitions, an entry left without definitions is dropped, and the lemma's entries join the results with the item's tags added to the rule chain, unless the same word is already found as well or better (`form_of.cpp` in the engine module). `YomitanSorter` applies Yomitan's full order including dictionary priority, with one key of the native lookup added: a headword reached only through a key without its marks or letters comes after the spellings found as written (`LookupResult.respelled`). The language's spelling variants (`LanguageSupport.spellingVariants`) and, when enabled, romaji converted to kana are looked up as well; `MappedText` maps their matched lengths back to the screen text. In a language written with spaces they include a word hyphenated at a line end, joined and with its hyphen kept. Other languages go through Yomitan's own language code: a bundle per language (`assets/yomitan-language`, built by `scripts/yomitan-language`) runs in QuickJS inside the engine library and turns the text into candidates with the language's text processors (such as decapitalizing) and deinflection rules (taken by the descriptor's code: Yomitan files its Georgian rules under `kat`, which its own lookup never reaches), and hoshidicts answers exact queries for them. Form-of entries (a form pointing to its lemma, which Wiktionary dictionaries hold by the million) are split out of an archive at import into a compact table next to the dictionary, memory-mapped for lookups (a catalog entry with `"build": "forms"` imports an archive for that table alone, its definitions left out and " (forms)" added to its title, for a language whose forms only the English edition lists); a candidate found there leads to its lemma, filtered by part of speech as in Yomitan, and the form's tags show as its rule chain, unless the text is that lemma itself (Croatian kuća, which Wiktionary also lists as its own genitive plural, shows no chain). The table also keys forms without the stress marks a language's dictionaries write (`LanguageSupport.headwordMarks`: Russian, Ukrainian, Belarusian, Croatian and Serbian; in Armenian the emphasis, exclamation and question marks on a stressed vowel), and in Greek, Hindi and Romanian every headword without its accent, nukta or letter marks (Romanian ă â î ș ț; a headword written with the cedilla letters ş ţ is keyed with ș ț as well), as a step back to itself, so text without accents and capitals find the accented headwords; Hindi headwords with candrabindu are keyed with anusvara as well, and Khmer headwords with subscript TA with subscript DA, which looks the same (`HeadwordMarks.replacements`). Lithuanian keys every headword twice: without the stress marks of its forms (žmogaũs; the dot over an accented i goes with them, that of ė stays: `HeadwordMarks.markBases`), then also without the marks of ą č ę ė į š ų ū ž (`HeadwordMarks.letterMarks`), and names the lemmas of forms without stress. Slovak keys every headword without the acute of á é í ĺ ó ŕ ú ý and the caron, circumflex and diaeresis of č ď ľ ň š ť ž, ô and ä (`HeadwordMarks.markBases`), so robit finds robiť after any word spelled so. Slovenian keys every headword without the tonemic marks of its forms (vôde, dẹ́lał: the acute, grave, circumflex, double grave, inverted breve, dot below and macron after a vowel, r or ə), with ł and ə as l and e (`HeadwordMarks.replacements`), then also without the caron of č š ž once those are gone, and names the lemmas of forms without the marks. Esperanto keys every headword without the circumflex of ĉ ĝ ĥ ĵ ŝ and the breve of ŭ (`HeadwordMarks.markBases`), and its bundle also looks the text up with the x-system read as those letters (cx as ĉ, ux as ŭ; `own-processors.js`). Arabic keys every headword (written without harakat, which its reading carries; the few that have them lose them) with ي for a final ى and ه for a final ة, and then with its hamza alefs (أ إ آ ٱ) as a bare alif (`HeadwordMarks.furtherReplacements`), so text without hamza finds the words written with it while a word written with hamza finds only itself; Yomitan's processors that put a hamza on the text's alif are replaced by none (`replacedProcessors` in `glue.js`), and the text's final ى and ة are looked up as ي and ه as well. Persian keys every headword with the Arabic ي ك ى as the Persian ی ک ی, ۀ as ه and without the zero-width non-joiner (a replacement by nothing), and its bundle reads the text the same way (`own-processors.js`). Hebrew keys the forms, which Wiktionary writes with vowel points, by their letters as well, and the lemmas they name lose their points; its bundle looks the text up without points and cantillation, and with an ASCII quote or apostrophe between letters as the gershayim or the geresh (`own-processors.js`). Kazakh keys every headword with its own letters as their Russian twins (қ к, ғ г, ң н, ұ ү у, ө о, ә а, і и, һ х), Kyrgyz with ң н, ө о, ү у, and the Kazakh bundle reads Latin i, I, h and ə inside a Cyrillic word as і, І, һ and ә; the text itself is not keyed, so text in the twins finds the Kazakh words while a Kazakh letter written in the text finds only its own spelling, and a headword reached through such a key (a tag-less form-of step) comes after the spellings found as written. A word that keeps some of these letters and loses others (Қазакстан) matches no key; when the text as written finds nothing as long as its first word, `DictionaryLookup` looks it up again keyed (`LanguageSupport.keyedSpelling`) and keeps the longer matches whose headword has the letters the text writes (`keepsWrittenLetters`, `keyedMatches`). Kazakh and Kyrgyz endings are the app's own rules (`own-transforms.js`, `turkicTransforms`), written from the grammar: a noun chain (plural, possessive, case, predicate person) or a verb chain (voice, negation, then a tense with its person, a participle, a converb, the conditional or the imperative) whose stem a hidden rule turns into the dictionary form; the texts between steps carry a private-use marker that the glue drops. Romanian article and agreement endings (consiliul → consiliu, aflată → aflat) are the app's own rules as well, matched to nominal entries and forms by their definition tags (`taggedRules` in `glue.js`); Wiktionary lists the forms of most Romanian words, so the engine drops the results that only these rules reach when the same text finds results without them (`LanguageSupport.inflectionRulesOnlyWithoutEntry`, `withoutRuleOnlyResults`), and a result that both a rule and a form row reach keeps the row's chain only. The Romanian bundle reads ş ţ as ș ț (`own-processors.js`), and Romanian results under a Cyrillic headword (the Moldovan spellings Wiktionary links words to) are dropped (`LanguageSupport.showsHeadword`). Latin's enclitics (-que, -ne, -ve) are the app's own rules added to Yomitan's Latin ones (`extendedTransforms` in `build.mjs`, `withOwnTransforms`), and the Latin bundle also tries v for a u before a vowel (`own-processors.js`); Latin takes the same entry filter, which leaves atque whole rather than at + que. Albanian's own endings (adjective forms, mediopassive verbs, participles, aorists, noun cases) are added to Yomitan's Albanian rules the same way and marked `fallback`: the glue gives each text they reach its rank and whether it must be a headword of its own (`fallbackRules`, `fallbackStep`), and the engine looks those texts up only when no other text found an entry, one rank at a time, stopping at the first that finds one (`candidate_lookup.cpp`). Swahili verb prefixes are the app's own rules (`swahiliTransforms`; Yomitan has no Swahili descriptor, and the bundle takes Czech's capitalization): the subject or negative prefix, the tense, a relative and an object come off from the outside in, and the stem is looked up as written, with ku- and with a hyphen, as dictionaries write verbs all three ways (alisoma → soma, kusoma, -soma). The texts between steps carry the private-use marker, the verb tag keeps only verbs and forms (`taggedRules`), and the engine drops these results when the same text has an entry of its own (`inflectionRulesOnlyWithoutEntry`). Welsh initial mutations are the app's own rules (`welshTransforms`; Yomitan's Welsh descriptor has capitalization only), one per mutation (soft, nasal, aspirate, h before a vowel): each applies only to the word as written, keeps at least two letters of the radical and matches entries of any part of speech (`untypedRules`), as Wiktionary's Welsh entries name none. The glue drops a word's rule candidates when its lowercase text is on the descriptor's `unmutated` list (mae, ar, dŵr: common words the rules would turn into others). The dictionaries' own mutation rows (`soft`, `nasal mutation`, the French edition's `lenition`) are shown under the rules' names, a chain the rule and a row both give once (`LanguageSupport.formTagRules`, `withFormTagsAsRules`); a single-letter lemma that only such rows reach is dropped (fara → b), and so is a chain of two mutations, the rule's step followed by the radical's own row (fara → bara → para), as a word takes one; the French edition's reversed `unmutated` rows are ignored (`ignoredFormTags`). Irish initial mutations are the app's own rules too (`irishMutations`), which replace Yomitan's noun eclipsis (`replacedTransforms` in `build.mjs`): lenition, eclipsis, t and h before a vowel, with the lowercase prefix before a capital (nGaillimh, tSín, hÉireann), one per word and with the same exception list (chomh, cheana) and row names (`lenited form`, `eclipsis`, `prothesis-h`); the French edition's `radical` rows, which lead from a radical to its mutated forms, are ignored. Irish in Gaelic type is read with consonant + h for a dotted consonant (`irishDottedConsonants`: ḃean → bhean), in any text. Finnish clitics (-kin, -kaan, -ko, -pa, -han) and possessive suffixes (-ni, -si, -mme, -nne, -nsa, a long vowel and -n) are the app's own rules (`finnishTransforms`), in the order the grammar allows (talossanikin → talossani → talossa), each leaving at least three letters; they match entries of any part of speech (`untypedRules`), as Wiktionary's Finnish rows name none, and the engine drops their results when the same text has an entry or a form of its own (`inflectionRulesOnlyWithoutEntry`: kuusi is no kuu with -si). An ending written after a colon (EU:n) belongs to the word before it (`LanguageSupport.wordStartOffset` with the text after the aim), and the lookup shortens to the word when no dictionary has the whole. Scottish Gaelic initial mutations are the app's own rules as well (`gaelicMutations`): lenition, with t-s for s after the article, n- before a vowel, named eclipsis as Wiktionary does, and t- and h- before a vowel, each prefix with its hyphen (an t-sràid, ar n-eilean, na h-Alba), one per word and with its own exception list (chan, bhathar) and row names (`lenition mutation`, `mutation prothesis-h`); the English edition's `mutation mutation-radical` rows, which lead from a radical to its mutated form, are ignored. The older spelling's acute is also read as the grave (`gaelicAcuteAsGrave`: mór → mòr), in any text. Welsh keys every headword without the circumflex, grave, acute and diaeresis (`HeadwordMarks.everyHeadword`; Scottish Gaelic without the grave and acute), and the engine drops a result reached through such a key when the same text finds another result (`LanguageSupport.respelledOnlyWithoutEntry`, `withoutRespelledBesideEntries`): ty finds tŷ, twr only twr, bith bìth. The lookup carries whether its text was recognized (`LookupOptions.fromOcr`: set by the overlay when the aimed word's engine is not app text, false for the search screen and dictionary links); a bundle with processors marked `ocrOnly` (`own-processors.js`: Welsh ý and û also read as ŷ and ŵ) keeps two processor sets and picks one by it. The lemmas Arabic forms name, which are vowelled, lose their harakat (`HeadwordMarks.lemmasAsWritten`), as headwords have none, and so do the macrons and breves of the lemmas Latin forms name (amat, a form of amō). Six exceptions to that filter: an English entry without a part of speech matches a verb form of a phrase whose second word is an adverb particle ("picked up" → "pick up"), a Bengali one matches any word with one of the app's own noun endings undone (`own-transforms.js`, one ending per word, as Wiktionary's Bengali entries name no part of speech), a Georgian one any word Yomitan's Georgian rules leave at three letters or more (`untypedRules` in `glue.js`; Wiktionary's Georgian entries name none either, and the rules chain down to single letters), an Arabic one any word Yomitan's noun rules (prefixes, ـة, plurals, possessives) leave at two letters or more, as Wiktionary's Arabic adjectives and adverbs name no part of speech either, and a Persian one any word the app's own Persian rules (an enclitic, then a plural, then a comparative ending; a verb prefix) leave at two letters or more, three after the prefixes ب and ن, as Wiktionary's Persian entries name none, and a Hebrew one any word the app's own prefix rules (ו ש כש ב כ ל מ ה, up to three letters in the order the grammar allows; Yomitan has no Hebrew rules) leave at two letters or more, for the same reason; the bundle's glue marks such candidates, and the interposed-object rule stays typed only. Wiktionary's Kazakh and Kyrgyz entries give their part of speech as a tag of the glossary instead: their noun chains match any entry, and a verb chain carries the tag `v` (the candidate's `g`), which keeps only the glossaries tagged with it (`has_tag` in `candidate_lookup.cpp`). A form written with leftovers of Wiktionary's templates is keyed by its words: a romanization or note after it is cut off, two spellings split by a slash are keyed both, an ending set apart is joined to its word, an Armenian classical spelling loses its label ("orthography spelling գիւղ"), and a form of an unfilled template (`{{{3}}}`) is not keyed (`form_headwords` in `archive_split.cpp`). Inflection template names among a form's tags (`ar-infl-a`) are left out of the tags shown, and an Arabic, Persian or Hebrew form written without the script's letters (a romanization, a Cyrillic Tajik spelling, a Phoenician one) is not keyed (`HeadwordMarks.formsInScript`). A language that writes the syllables of a word apart (Vietnamese) or no spaces at all (Thai and Khmer, from the ICU segments, passing over zero-width spaces and a repetition mark the segmentation parts from its word) starts the lookup at the one and two words before the aimed one as well (`LanguageSupport.earlierStartOffset`, `wordStarts`): `DictionaryLookup` keeps from those starts only words that reach the aimed one and puts them first (`fromEarlierStarts`), and each result's `start` tells the overlay where its word begins on screen. Persian starts at the word before only where the two are one word written apart, the verb prefix می or نمی before the aimed word or a plural or comparative ending (ها, های, تر, ترین) as the aimed word, and its bundle tries such text joined. The segmentation may also join two words a dictionary has apart into one (Khmer ក្រុងភ្នំពេញ, which dictionaries have as ក្រុង and ភ្នំពេញ): when no result covers the aimed character (`aimedCharAt`), Thai and Khmer start the lookup at each letter cluster inside the aimed word up to it as well (`LanguageSupport.innerStarts`), and the words of the first start that cover it come first (`reachingAimedCharacter`); the overlay keeps the shown results while the aim moves inside the same word, unless they came from inside it and do not cover the new character. Every language written with spaces starts the lookup at the first half of a word hyphenated at a line end as well when the aim is on its second half. When the aim is on a later part of a word written with a hyphen (owned in state-owned), the lookup also starts after each hyphen before the aimed character (`LanguageSupport.partStarts`): the results from the word's start that cover the aimed character come first, then those of the parts that cover it, and the first part's own results (state) are dropped unless no part finds anything (`withHyphenatedParts`); the overlay keeps shown results only while the aim stays in the same part. In Kazakh and Kyrgyz a hyphen after digits, two capitals or a unit (1990-ға, АҚШ-қа, км-ге) is a start as well, so the ending is also looked up with its hyphen and finds suffix entries (-ға); in Finnish only a hyphen after digits is (1990-luvulla, 20-vuotias), as after an abbreviation it joins a compound (EU-maat). Results reached only through form-of entries with a tag the language ignores (`LanguageSupport.ignoredFormTags`: Vietnamese and Thai `classifier`; Kazakh and Kyrgyz `Arabic`, `romanization` and `Yañalif`, rows that only give the word in another script) are dropped. From one start, Thai and Khmer keep the longest match and the shorter ones that end at an ICU word boundary, never one that ends inside a letter cluster (`LanguageSupport.shownMatchLengths`). The same word (expression and reading, compared as the language's Yomitan reading normalizer does: pinyin without spaces or apostrophes) from several dictionaries or spellings becomes one result in the place of the first. A language written in two scripts (Chinese) tags each result with its script (`lang`, which picks the glyph forms on the page): the word's own, else the text's, else the one chosen on the Languages screen; `ChineseScripts` decides by the characters only one script uses and converts text character by character, from a table that `scripts/chinese-scripts/build.py` generates from Unihan and CC-CEDICT. A form-of entry that only spells its lemma in the other script (Wiktionary's `Simplified-Chinese`) shows the spelling that was read, so it merges with dictionaries that list that spelling; with one script fixed, the text is also looked up converted, and a word gives way to its spelling in that script. A typed search in a language with a reading search (Chinese pinyin, `LanguageSupport.readingKey`) also finds words by their reading: at import, `ReadingIndexBanks` writes a `ReadingIndex` next to the dictionary, a memory-mapped file of the words of each toneless key, the likely common ones first (a character that more of the dictionary's words contain counts as more common); `DictionaryLookup.lookupQuery` looks up the first 80 words of the query's key in the chosen script, keeps those whose reading has the key, and ranks the tones and apostrophes typed (`readingMatch`) before Yomitan's order. Characters of the matched word that a character dictionary describes (Japanese kanji, Korean hanja; `LanguageSupport.singleCharacterEntries`) follow the results as entries of their own, and a text that matches no term shows the entry of its first character (`characterEntry`), with the dictionary's tags for it (jouyou, basic hanja for education).
5. **Render.** The overlay sends the results as JSON to the lookup page in a pre-warmed WebView. The WebView keeps the last frame of the view it showed, so a popup opened again stays transparent and lets touches through until the new view is ready to draw (`LookupPage.whenDrawn`: a visual state callback after the render script, at most 600 ms), and an open popup moves to a new word only then. The page builds the cards; glossaries go through `YomitanRender` (structured content, images served from the engine, each dictionary's `styles.css` scoped to its own entries). `&quot;` and `&apos;` that a dictionary's packaging left in plain text show as quote marks. Headwords get their reading as ruby: Japanese through `YomitanRender.furigana`, languages with a syllable per character through `HeadwordReading` (`reading-zh.js` splits pinyin into syllables with their tones, one above each character where they match up); a Russian reading that only adds stress marks takes the word's place (`reading-ru.js`), as does an Arabic reading that only adds harakat (`reading-ar.js`); a Persian reading, a Latin romanization, follows the word in the headword line instead (`reading-fa.js` through `HeadwordReading.after`). In a language written right to left (`LanguageSupport.rightToLeft`, the state's `rightToLeft`), the recognized text and the headwords get `dir="rtl"`, and a glossary and each of its blocks `dir="auto"`, so every block takes the direction of its own first letter (an Arabic example among English meanings) while the layout stays; a dictionary's name gets `dir="auto"` as well, so its Latin letters do not set the direction of the block it starts. `overlay/fonts` supplies the page's `lang`, the phone's font for the language declared by its local name and limited to the script (for Hindi, Bengali, Georgian, Armenian, Thai, Khmer, Arabic, Persian and Hebrew only the serif one, as the default font falls back to the phone's font for the script by itself; Android declares those for the script, `und-Deva`, `und-Beng`, `und-Geor`, `und-Armn`, `und-Thai`, `und-Khmr`, `und-Arab` (Persian's as well) and `und-Hebr`, which `SystemFontFiles` counts as the language's; a font whose weight axis does not reach the normal weight declares no range), downloaded or added fonts (limited to the script unless chosen for all text), and the user's CSS, applied last with the page's font list appended to each `font-family`. The page's content security policy lets only stylesheets and fonts come from the internet; scripts, images, media and requests stay on the page's own host.
6. **Highlight and placement.** The matched length of the first result decides how many characters are highlighted. `PopupPlacement` puts the popup above the word, else below the bubble, in landscape beside them on the side with more space (shrinking a little); when that does not fit, the popup keeps its size at the screen's edge on the roomier side and covers part of the word or the bubble rather than getting low or narrow.

Aiming again only repeats steps 3–6; the screen is not scanned again until the bubble goes back to the dock or is tapped.

### Lookup source

`LookupSources` (core:photos) says what the bubble reads, one source at a time: the screen (the steps above), a recognized photo, or nothing (a page that shows photos while it has no recognized one). A page that shows photos opens a presentation while it is in the foreground and closes it when it leaves; the screen is the source otherwise. Every change of source, photo or recognition takes a new generation; moving or zooming the photo keeps it. The overlay reads the screen only through `ScreenReads`, which lets a capture, an app text read or the cloud connection through only while the screen is the source of the scan's generation, and drops a screenshot or app text that finishes after the source changed. Over a photo the bubble takes its stored text with no screenshot, recognition or app text: the layout stays in the photo's pixels and `TextFrame` maps the aim into it and the highlights and the popup's anchor back, cut to the part of the photo that shows. The photo's text is looked up in the language it was recognized in, which the bubble's glyph shows, and the bubble menu offers no languages. When the photo moves under a resting bubble, the highlights and the popup follow it (the popup's window moves without a new render) and the aim is tested again. Leaving the photo docks the bubble, or closes its scan and docks it when the finger lifts if the bubble is being dragged (back over a photo before that, it stays out); a photo shown while the bubble is out over the screen replaces the scan with its text. A note's picture comes from that source: a retained screenshot or the original photograph.

### Camera page and image ownership

Photo OCR is separate from screen drafts and refinement. By default a photo is read whole once, scaled down to
1500 px on its longer side, as its only region (`PhotoOcrSettings.tiled` false). With High accuracy (Camera settings,
`CameraPreferences.highAccuracy`) or Recognize more accurately in the ⋮ menu, `PhotoTiles` covers the original pixel
space with overlapping regions; `PhotoAssembly` keeps each physical word once across tiles and lines (complete words over
words cut by a tile edge, longer readings over the shorter ones they contain; a cut word covered by complete ones is a
misreading of them; a word ending within a glyph of an edge along its line counts as cut, as an engine may drop the cut
glyph; a glyph's length counts marks with their letter), joins line and paragraph fragments (a shared word joins them
also where a slanted line's boxes are offset; parts of differing direction, such as a tile's part of an Arabic line
that holds only a Latin name, take the language's direction) and words cut by both tiles (in the word's own direction,
so a Latin word inside an Arabic line joins too), retaining
character boxes, logical word order and per-word engine provenance. A photo of more than one tile is also read whole, scaled down to the
tile size (`PhotoTiles.overview`); assembly takes from it only words larger across their line than the tiles' overlap
that lie whole in no successful tile, and drops the tiles' words lying at least half inside them. The overview is not
a region: the progress, the region counts and the failed regions leave it out, its failure only loses such large
text, and alone it replaces no text (a photo with text keeps it until a region succeeds; one without text gets the
large text, if there is any). `TextLayout` builds an
immutable spatial index on its first hit test, with the same selection and tolerance as the previous linear hit test;
a photo's layout builds it in the background with the layout (`prepare`). A pinned device session fixes a photo attempt's
local model. With both engines a tile is read by the cloud alone, and by the local model only when the cloud fails
(the cloud's error is kept when both fail), so a photo is not as slow as the device; the image is released once that
read terminates. `PhotoRegions` retains the source file and serializes EXIF-aware region decoding, at original resolution or
scaled to a given size (a power-of-two sample, then a filtered scale); a note's crop of a photo is scaled to at most
4 megapixels this way;
`PhotoRecognitionJobs` limits processing to two tiles at once, independently of screen small-text settings.

Each attempt fixes its document, language and settings. Successful tile pages and failures are written atomically to
a separate progress file, without changing committed lookup text. Room v2 stores its pointer (migration from v1).
After all work terminates, the assembled snapshot replaces committed text once, including usable partial results.
Version 4 snapshots store whether the photo was read by tiles; versions 1 to 3 read as tiled, and version 3 and later
retain raw tile observations. The pending change of the strip compares engines and model, and the reading only where
tiles would read more: a photo read whole is out of date while High accuracy is on, unless it is a single tile anyway;
one read by tiles is not while it is off. Retry keeps successful tiles and processes
only missing regions. A process-owned job survives page disposal/backgrounding and cancels on replacement; stored
progress never restarts itself after process death. Camera preferences have their own no-backup DataStore and survive
settings reset, independently of photograph storage.

The app shell has one NavHost inside a Scaffold with Home, Search, Camera and Settings tabs. Tab switches save and
restore each tab's navigation stack; screens consume the bar's insets. First-launch setup and the debug viewer hide
the bar without replacing the NavHost. Requests from outside the app (Anki settings, Dictionaries, a language's models)
open their page in the Settings tab, on the language the request names (the popup's, which over a photo is the
photo's) or else the active one; the same page already on top is replaced, as its view model keeps the language it
opened on. During the first-launch setup they open over it instead, and the bar stays hidden until the setup ends at
Home, since a tab switch clears the back stack under it.

`CameraViewModel` observes `PhotoDocuments.current` and owns the capture/replacement operation and the temporary
retake state. CameraX's `LifecycleCameraController` and `PreviewView` live in `app`, bind only while capture is shown,
and release on disposal. Besides preview and capture, the controller runs a small (about 320×240) analysis stream:
about ten frames a second are reduced to a few dozen pixels and drawn, blurred, around the fitted 4:3 preview. The
e-ink theme turns this stream off. A capture uses the store's staging file and replaces the document only after CameraX's
terminal callback and validation; cancellation waits for that callback before discarding the staging file.
The document's lifetime is independent of the page, camera permission and accessibility service. After successful
replacement, `CameraRecognition` checks readiness with an explicit image source and starts recognition. Accessibility
text settings cannot bypass image OCR requirements; cached photo lookups require dictionaries rather than a model.
Language/settings changes show pending state and require explicit recognition. A status strip above the viewer holds
the language chip, the partial-result warning, Recognize, the status line and progress (`cameraStatus` is its pure
model). Top-bar actions enter overflow when their measured touch targets do not fit; Save to gallery always stays
there. When the strip changes height, `PhotoViewport.resized` keeps the zoom and the photo point at the center.

`PhotoViewer` decodes a sampled display bitmap off the main thread and draws the stored pixels through an EXIF and
viewport matrix, without rotating or copying the original image. One-finger pan and two-finger zoom update a bounded
viewport from fit through 8× fit; zoom also decodes only the visible region for sharp display. Reopening fits again.
It publishes the photo's measured screen bounds only
after decoding. `CameraLookup` presents a source from the start of the page's entry (before it resumes) until it
pauses: a committed recognition snapshot and viewport, or no text for preview, loading, failed decoding, dialogs and an
unrecognized photo. Leaving the page or backgrounding closes the source. The overlay cuts highlights, margins included,
to the photo's visible part.
Old-document viewport callbacks are ignored. The display bitmap's sample does not alter stored OCR coordinates.

`PhotoDocuments.pinImage` keeps the original pixels readable, so a note or export can finish after the current photo
is replaced or deleted: the store counts open images per photo and defers deleting a pinned photo's files until the
last one closes. The owner closes the `PhotoImage` after its reads; files an abandoned image kept are deleted before
the first store change after a restart. Preview and crop reads decode regions off the main
thread, apply EXIF orientation, and retain unpublished bitmap ownership through cancellation.

`NoteContext.image` accepts a screen or photo `NoteImage`. The screen adapter retains the existing shared screenshot
and its natural screen placement; the photo adapter owns a sampled upright preview and crops original pixels.
`CropPlacement` maps an editor selection back to source coordinates. Photos fit above the controls; screenshots keep
their existing placement. Closing a scan also invalidates a preview still being decoded, preventing a late editor.
Photo note requests capture their recognition snapshot, sentence and language and reject stale source generations.

`PhotoGallery` pins the original and writes its ordinary bytes to a pending MediaStore image in Pictures/Screenlate.
Only a complete write and stream close publish the image. Failure/cancellation deletes the pending row. The explicit
Camera action reports success/failure, does not recognize again, and leaves the exported copy independent of private
document deletion. No OCR sidecar, backup integration or broad storage permission is added.

`PhotoImports` (`PhotoImporter`) copies an image from the system photo picker or the share sheet into a capture file
of the store. A file `BitmapRegionDecoder` reads (JPEG, PNG, WebP, HEIF), as the viewer and recognition need, keeps its
bytes and EXIF orientation; anything else is decoded with `ImageDecoder` (orientation applied, sRGB, scaled to at most
24 megapixels) and stored as PNG, and a file it cannot decode is rejected. `CameraViewModel` then takes it the way of a
capture (`replaceCurrent`, recognition, automatic saving); when the current photo is not in the history it first
holds the copy and asks (`CameraState.askingImport`). Picker results and shared images queue until the photo is
loaded and the page is free. "Share → Screenlate" reaches `ShareImageActivity`, which runs in the sending app's task
and passes the image, with a read grant in the clip data, to the main screen in the app's task; `MainActivity` hands
it to `SharedImages` and selects the Camera tab, except during the first run. Being exported, the activity reads the
share through `IntentSanitizer` and takes only another app's `content:` link, so a sender cannot make the app read its
own providers or files; the provider is compared without a user prefix (`0@`), as the system finds it. Any app can
start `MainActivity` as well, so it checks the link again.

`PhotoHistory` (implemented by `PhotoStore`) keeps photos apart from the current one without copying them: a photo
row has `saved`, `savedAt` and the language of its last recognition (Room v3; the migration orders earlier rows by id
and leaves the language empty until the next save reads it from the snapshot). Replacing or closing the current photo
deletes it only when it is not saved. Saving writes a 320 px upright JPEG thumbnail (`PhotoThumbnails`) and then
trims the history to `HistoryLimits`: a count and a size in megabytes (10^6 bytes), 0 meaning none, counting the
image, thumbnail and text files, oldest saved first, the latest always kept. Opening a history photo makes it current
with its stored text and no recognition. A photo that leaves the history, by removal, trimming or clearing, is
deleted; the current one is closed first, and the Camera page shows the live camera. `CameraPreferences` hold
automatic saving and the limits. `CameraViewModel` saves after a capture when automatic saving is on; the history
page (`PhotoHistoryViewModel`) and Camera settings (`CameraSettingsViewModel`) reach the store through the same
interface. `closingAsks` decides when closing or opening another photo first asks to save or delete an unsaved one.

## Anki export

The page builds the dictionary markers of an entry (glossary HTML with scoped CSS, furigana, pitch, frequencies) because it already has the renderer. Glossary HTML comes from the renderer's tag allow-list with escaped text; each dictionary's scoped CSS goes into a `<style>` element with any `</style` written as `<\/style`, so a dictionary cannot end the element and add markup to the card. `PopupNotes` adds the sentence and cloze markers from the OCR paragraph, the audio clip and, on a long press, the cropped screenshot. The sentence and the crop frame come from the view shown when ➕ is pressed (`NoteSource`); until the scan's final result ➕ is grey and only explains itself (`noteWaitsForText`, the page state's `noteWait`), except for a word from the app's own text; a new scan closes the previous popup; a note that finishes after its scan closed stays out of the next scan (`ScanNotes`); `AnkiNotes` renders the field templates, handles duplicates and talks to AnkiDroid through its content provider; its `check(language)` asks AnkiDroid about each part of a language's setup for the Anki page's connection check, read-only. A newly chosen note type gets its templates from `FieldTemplate.guess`: a `NoteTypePresets` entry when the note type's name and fields match a well-known mining note type (its authors' templates, with this app's nearest marker where they use their own), otherwise Yomitan's rule of whole field names with aliases, the note language's own field names first (`LanguageSupport.ankiFieldNames`: Pinyin, Traditional). A language written in several scripts has a marker for the word in each (`LanguageSupport.scriptMarkers`), which `PopupNotes` fills through `DictionaryLookup.inScript`: the character table's conversions, the first one a dictionary lists with the word's reading. Furigana of a language with a syllable per character use the same `HeadwordReading` rules as the headwords; Russian stress marks go into the word, in a sentence only into words written in their dictionary form (`HeadwordReading.sentenceSegments`). The + menu offers the furigana markers only where `LanguageSupport.furiganaMarkers` is set (Japanese, Chinese, Russian). In a language written right to left, suggested templates and the + menu put the markers of the language's own text (`LanguageSupport.rightToLeftMarkers`: the word, the sentence and its cloze parts, Arabic's vowelled reading) in `<span dir="rtl">` (`FieldTemplate.rightToLeft`, `withMarker`): markers with only tags between them share one span unless it would cut a tag apart, a template that sets a direction is left alone, and the first field gets none, as AnkiDroid's duplicate check compares its markup. Wiktionary and Lingua Libre recordings come from the Wikimedia Commons search (`AudioFinder`, `AudioPages`): a search narrowed by the title word, then a regular expression on the file titles; an error answer (too many regular expression searches) fails the source instead of meaning no recording. A search that matches a redirect gives its target, kept only when it records the same letters. Where titles may add vowel marks (`LanguageSupport.recordingMarks`: Arabic), every letter of the expression may carry them (Lingua Libre's then without the title word, which the index files vowelled titles under other words for), term and reading are compared in NFC as Commons stores titles, and each clip gets a rank: 0 the word as written, 1 the dictionary's vowelled reading, 2 the rest. `find` takes the lowest rank, then the highest source, and keeps a result short of rank 0 only when no source failed. Media files go to AnkiDroid through a FileProvider.

## Sentence translation

`core:translate` talks to three keyless services: Bing (a key read from the translator's web page, kept for its lifetime and fetched again when the service refuses it), Google's `gtx` endpoint and the translator built into Edge (Microsoft's language codes, no key). Each `Translator` knows its language codes and longest text. `SentenceTranslator` runs the services in the user's order and moves to the next one when a service fails or gives no answer within 3 s; it reports either the text with its service or every service's `TranslationError` (a kind; for HTTP errors the status; for the logs a detail without text, such as an unexpected answer's shape). A certificate that is not valid at the device's date has its own kind, so the user is asked to check the clock. A request runs in the translator's own scope: callers asking for the same text share it, and a success is kept for 10 minutes (16 entries), so a note gets the translation the popup shows. The target is the chosen language or the interface language (`TranslationLanguages.defaultFor`, English when it is the source language).

In the overlay, `SentenceTranslation` connects it to the page and to notes. The translation button on the page calls `onTranslate` with a request number; the controller translates the first view's sentence (the same one a note would take) and answers with `showTranslation` (the text, its service and the sentence for the copy button), which the page ignores when it no longer shows that request. The page state carries the view's sentence: a new scan result shown while the popup stays open (`render` with `continued`) keeps the translation when the word and the sentence are the same, and anything else drops it. `PopupNotes` asks `SentenceTranslation.forNote` when ➕ is tapped, so the request runs while a crop editor is open, and fills `{sentence-translation}` once the note is ready, waiting up to 5 s more and leaving the field empty otherwise. The settings page's test calls each service separately with a 15 s limit and keeps nothing.

## Dictionaries

`DictionaryRepository` is the only writer of the registry. Imports (bundled archives, files, downloads, Yomitan collection exports) run as foreground WorkManager jobs: the archive is converted into a staging directory, moved into `files/dictionaries/<uuid>/`, registered, and the engine is reloaded. The jobs run on two unique chains (`DictionaryImports.QUEUES`, `APPEND_OR_REPLACE`), a new job going to the chain with fewer unfinished jobs, so a download that stalls holds up only its own chain; each chain's job has its own notification. A job reads only its own input (`OwnInputMerger`): WorkManager's default merger lays the outputs of the job before it in the chain over the input, and a stopped download's output carries its URL, archive and entry for Resume. The import steps (the engine's import of an archive, a model install, a whole file, collection or bundled install) take a process-wide mutex (`DictionaryImports.importing`), as the native importer needs a lot of memory: a job waiting for it shows as waiting, and a death of the process meanwhile does not count against it. Queueing runs under another mutex and awaits WorkManager, so the next job queued sees the previous one: `download` and `downloadModel` first look for a job tagged with the same catalog entry or URL and return an unfinished one, or resume a stopped one that is still listed. The engine keeps neither tag descriptions nor the tags of phonetic transcriptions, so the import reads them from the archive into files next to the engine's (`TagBanks`, `TranscriptionTagBanks`): the transcription tags are kept as one long per tagged transcription (39 bits of a hash of term and transcription with the index of its tag set), sorted for a binary search and memory-mapped rather than read: a Wiktionary transcription dictionary has millions. The import collects them in sorted chunks and merges the chunks into the file. A lookup turns them into regions (`TranscriptionRegions`: flag emoji, and accent names per language) and cleans the list up (`Transcriptions`); those whose tags the language puts first go before the others (`LanguageSupport.firstTranscription`: Hebrew's Modern Israeli ones), and the page orders the transcriptions by the user's audio regions. A catalog entry that names a `build` (a wordfreq word list, or a corpus' word counts where wordfreq has none: Thai) is downloaded like an archive, checked against its SHA-256 and converted into a dictionary archive (`WordfreqDictionary`, `CorpusCountsDictionary`; a language written in two scripts also gets each word's spellings in the other one with its rank, as wordfreq writes Chinese in Simplified characters only) before the import; the frequency dictionary then sorts its language's results unless another one was chosen (`DictionaryRepository.preferSortDictionary`). A dictionary with the same title, or the one an update was started for, is replaced in place. A failed import is reported on its task and does not stop the imports queued after it. Before the engine imports an archive, its title is checked: the engine writes into a directory named after it. An import the process died in is run again by WorkManager, from the start, once: a job whose `runAttemptCount` shows two earlier runs ends with an "interrupted" result instead, so an archive that kills the process cannot loop. As every app start queues the bundled install again, an interrupted bundled install also pauses it until the app's install time changes (an update); the task's "Try again" and a dictionary reset end the pause. "Cancel" on one task stores its id in the preferences (the process may die before the job ends) and cancels the job's body, which runs inside `CancellableRuns`, without cancelling the WorkManager job: a cancelled job ends successfully, so the jobs queued after it still run (cancelling it in WorkManager would cancel them too). Downloads and collection conversions check for the cancel between reads; the import notification's Cancel action goes through the same path (`ImportCancelReceiver`). A download job has a network constraint (`ImportTask.needsNetwork` until it starts; `DictionaryImports.online` follows the default network as the constraint does, internet access the system validated, for the "Waiting for a network" cards) and the least linear backoff, 10 s a run (WorkManager counts every run, also one it stopped, and starts the next no sooner than the backoff after the enqueue, so the default exponential one would hold a download back longer after every lost network); it writes into an archive named in its input (in `no_backup/dictionary-downloads/`, which the system does not clear as it does the cache), so a later run continues it (`ResumableDownload`: a range request with If-Range on the first response's strong ETag or Last-Modified; a state file next to the archive keeps that validator and whether the download finished, so a run after a death during the import does not download again). When the network goes during a download (the default network is not validated, now or within 2 s of the failed read), the failure is not a break-off and counts as no retry: WorkManager stops the job for its network constraint (stop reason 7) and runs it again once a network is up, continuing the archive; a job it does not stop keeps waiting in its run and tries the download again every 30 s. A job stopped during its import step keeps the finished archive, which the next run imports without downloading it again. A download that breaks off while the network stays up (the read timeout is 20 s) queues a copy of its job at the end of a chain (`DictionaryImports.requeue`: the same input and archive, its retry number in the input and a tag, an initial delay of 30 s doubled with each retry) and ends with a "requeued" result, which the task list leaves out; a copy queued while the job was cancelled or stopped by WorkManager is cancelled again at once. Before a job returns its result, it records it in the preferences (`DictionaryImports.recordEnd`, the output's bytes per job id, dropped once the job has finished): WorkManager drops the result of a job it stops at that moment and runs the job again, and that run returns the recorded result at once, so a job that was requeued, gave up, failed, was cancelled or finished is never run again. After three retries, as after an HTTP 4xx or a failed import, the job ends with a resumable result that carries its input, and `DictionaryImports.resume` queues it again. Runs that die while downloading or waiting for the import mutex are counted like system stops, so only deaths during the import count towards the two runs. Finished tasks are dismissed one by one (their ids are kept in the preferences until WorkManager prunes the job); dismissing a stopped download deletes its partial archive; the engine's import of an archive runs to its end, and the repository checks again before it registers the result. A cancelled or given-up job deletes the copy of the picked file it was to read and gives back the kept access to it. Each job is tagged with the name of the archive it reads, and the first import job of a process removes what earlier processes left: directories of no registered dictionary, staging directories, and downloaded or copied archives (with their state files) that no unfinished job or stopped download reads (when an unfinished job from an older version has no such tag, only archives older than six hours), also in the cache folder older versions kept them in, which goes once it is empty. Orphaned directories are listed under the registry lock, so the list never holds a dictionary between its move and its registration, and deleted after it, so lookups do not wait for large deletions.

A Yomitan collection export is one JSON file with the rows of all dictionaries, table by table. `YomitanBackup` reads it twice as UTF-8 bytes without decoding row values: first to measure the chosen dictionaries (`measure`), then to copy their rows into one Yomitan archive per dictionary (`convert`). `CollectionSpace` turns the measurement into the peak storage of the import (all archives exist before the first one is imported, each is deleted after its dictionary is installed) and decides whether the archives are stored uncompressed (fastest), deflated (when only that fits), or not written at all (the task fails with the needed and free space).

`DictionaryReset` returns the dictionaries to a fresh install. No screen starts it any more (the Dictionaries screen has no reset); it finishes a reset that an earlier version left interrupted. It cancels the import jobs by tag and waits until no worker is inside its body (`DictionaryImports.cancelAll` counts them), forgets the bundled installs, deletes every dictionary through `DictionaryRepository.deleteAll`, and queues the bundled archives again. Before it deletes anything it stores the number of the run in the preferences and removes it once the bundled archives are queued; `resumeInterrupted`, called at app start, runs the reset once more after a first run the process died in, and after a second one gives up and stores a flag. The start screen shows that flag once in a dialog, and the Dictionaries screen as a card until it is closed or a reset succeeds. The queued install continues as any import does. A reset that fails with an exception is reported on the Dictionaries screen and not run again by itself. `phase` (deleting, then installing until that import job finishes) drives the spinner at the top of the Dictionaries screen.

## Settings reset

All settings live in one preferences DataStore. Its provider keeps the settings as last read (`SnapshotDataStore`), and every repository offers a `cached` value from it, so a screen's first frame shows the user's values rather than defaults that change a moment later; reads and writes still go through the DataStore. Data from outside the settings is kept the same way while the app runs: AnkiDroid's last answer (the Anki screen shows it dimmed and without taps until AnkiDroid answers again, `Modifier.pending`), the Dictionaries screen's last state, the dictionary list, the launcher apps and the popup's typefaces. `SettingsReset` removes stored keys rather than writing defaults; `SettingsKeys` maps key names to the settings page that resets them (the global reset also clears update announcements and one-time hints). Dictionary bookkeeping, migrations and the interface language (kept by Android) are never touched. Leaving e-ink mode goes through `EInkSizes.restore`, and the Background page's reset also stops the keep-alive service. The popup CSS editor saves after a pause, so its reset first replaces the pending text with the default; text fields that keep their own copy (the Anki tags) take the new value once they lose focus, and confirming a reset clears focus.

## Backup and restore

`app/backup` writes one zip: a manifest (format version, app version, the sections it holds, its languages and recognition models) first, then the preferences of the chosen sections as typed JSON (`BackupPreferences`: key prefixes decide the section; internal state such as one-time hints is left out), the dictionary list (registry entries without ids, matched by title on restore, each with the size of its files), the chosen popup fonts (`fonts/fonts.json` and their files, `FontBackup`), the files of each recognition model (`models/<id>/`, which versions before them skip), and each chosen dictionary's converted directory. The choice is a set of sections plus, for languages, fonts and dictionaries, `FileChoice`: the item's mark and the files marked otherwise, so a file added later takes the item's mark; `BackupChoiceStore` keeps the last choice in preferences outside the backup. A language left out takes out its own preference keys (`SettingsKeys.languageOf`), its dictionaries (by source language) and sort dictionary, the catalog fonts of its language and the models no chosen language uses; dictionaries without a language and the user's own fonts are shared. Japanese's audio key also holds the volume and autoplay every language shares, so without Japanese only those two values go in and come back (`SharedAudioSettings`). The turned-on languages stay in the General section, limited to the chosen ones; restoring General adds the chosen languages to the turned-on ones and takes the backup's active language, stars and flags only for them (`BackupLanguages.merged`), so no language is turned off. A backup of an older version has no language list: its turned-on languages (Japanese alone without them) and the languages of its dictionaries and fonts stand for it. Opening a backup reads its head up to the first model or dictionary file, which lists the fonts with their sizes, also in older backups whose fonts belong to the popup section. Restoring reads the zip as a stream: checked preference sections are replaced in one DataStore edit for the shared keys and the chosen languages' own, the chosen fonts, models and dictionaries are staged and handed to `PopupFonts.restore` (merged into the installed fonts by id, files no font uses are deleted), `OcrModelStore.restore` (skipped when the same version is installed) and `DictionaryRepository.restore` (a dictionary with the same title is replaced in place and keeps its id, switch and priority), and the dictionary list entries of the chosen languages are applied last to whatever is installed. `BackupManager` is a singleton with its own scope, so the work goes on when the screen is left.

## Updates and releases

`update/AppUpdates` reads the latest stable GitHub release, picks the APK for the device's ABI, checks that it is a newer Screenlate signed with the same certificates and installs it through `PackageInstaller` (`UpdateReceiver` gets the session status). The version comes from git tags: `vX.Y.Z` gives the name X.Y.Z and the code X·10000 + Y·100 + Z (`build-logic`'s `ScreenlateVersion`). CI (`.github/workflows`) builds and tests every push, and a tag builds per-ABI and universal APKs, a source archive with submodules and a changelog for the GitHub Release.

## Languages

Language is a parameter of OCR, lookup and rendering (`core.common.Language`). Whatever differs between languages lives behind `LanguageSupport`; Japanese, English, Chinese and Korean are implemented so far.

`LanguageProfiles` (`core:common`) keeps the turned-on languages, the active one, up to two starred quick languages and the chosen flag countries in the preferences; activating a language moves the stars in the same write (a starred language swaps roles with the active one, any other takes its star). Each language support class lists its flag countries; `Flags` (`overlay`) maps them to the round flag drawables that `scripts/flags/circle_flags.py` generates from circle-flags, used by the bubble menu and the app. Settings kept per language use their old key for Japanese and the key with `_<code>` for other languages. Languages that read the same dictionaries share their dictionary code (`Language.dictionaryCode`): Croatian (`hr`) and Serbian (`sr`) both read the Serbo-Croatian ones (sh), the code that dictionaries, the catalog's dictionary entries, the Yomitan bundle, wordfreq, cloud recognition and backups use, while settings, models, voice and flag go by `Language.code`. The dictionaries count among a language's files only while no other language reading them is on (`LanguageFiles`); with both off, their files share one card under "Turned off". A language may also read another language's term dictionaries as a fallback (`LanguageSupport.fallbackLanguage`: Slovak reads the Czech ones, as Wiktionary's Slovak dictionaries lack many common words): `isReadBy` counts them among the language's dictionaries on the Dictionaries screen, in `LanguageFiles`, `LanguageSwitch` and backups, and `LanguageSetup` lists the fallback's main dictionaries after the language's own, unticked and outside the mandatory check. `DictionaryRepository` loads them with the language's own, and `DictionaryLookup` keeps the results of the language's own dictionaries without the fallback's definitions (`preferringOwn`); only when those find nothing does it show the fallback's results, each marked with the fallback's code (`LookupResult.fallbackLanguage`), which the popup shows as the language's name after the word. Serbian is written in both scripts: its support class decides per line which one OCR text is in (`LanguageSupport.ocrLines`), gives the voice Latin words in Cyrillic and the translation services Latin text as sr-Latn, and looks for Wiktionary recordings under both spellings. The application settles the first run before anything writes preferences: any stored preference or installed dictionary means an upgrade, which keeps Japanese on and, in the same write, keeps the translation button on unless it was turned off (it is off by default on new installs; a restored backup without the button does the same); a fresh install opens `FirstRunScreen` first. Its result and the check behind "Turn on" on the Languages screen reach the screen as one-shot events from the view model, so a screen recreated meanwhile still navigates. `LanguageSwitch` (`app`) turns a language on, queueing the downloads chosen on `LanguageSetupScreen` as ordinary imports, and off, optionally deleting its dictionaries and models and cancelling their unfinished downloads. The APK carries no bundled dictionaries: Japanese gets its dictionaries from the catalog like any language. `BundledDictionaries` remains for installs from versions that shipped them (Japanese, installed only while Japanese is on); their copies stay, and when their files are missing the start screen offers the catalog download. A catalog entry can also name an archive the app carries (`asset:///`, the Korean hanja dictionary built by `scripts/hanja` from Unihan): it is chosen on the setup screen like a download, but the import copies it from the APK without a network constraint, and the download total leaves it out. A dictionary belongs to its source language, which an import takes from the matching catalog entry first, then from index.json (where Wiktionary's `all` names no language), then from the replaced dictionary, then from the archive's content. The start screen reports, per turned-on language, the mandatory catalog categories that no enabled dictionary covers, with the progress of the queued imports.

On-device recognition: ML Kit's Latin, Japanese, Chinese, Korean and Devanagari models are bundled; each script gets its own recognizer (Latin-script languages the Latin one, which is as accurate as the Japanese model on Latin text and twice as fast; Bengali the Devanagari one, which reads both scripts). A script without an ML Kit model needs a `ModelOcrEngine`, whose code is in the APK and whose models are catalog entries of the category `OCR_MODEL`: the import worker downloads them like dictionaries and hands them to `OcrModelStore`, which installs a file only when its SHA-256 matches the pinned one, unpacks zip archives, keeps a version per model and replaces an older one. Several languages may share a model (a text detector); turning a language off deletes only the models no other turned-on language uses. `DeviceOcr` asks ML Kit first, then the engines whose installed models read the language; a language the device cannot read goes to the cloud alone, and a device-only scan of it fails with a message. Lines carry their direction: a horizontal line whose first strong character is right-to-left is split into characters from its right edge.

Engines with downloaded models: Tesseract (Tesseract4Android, one traineddata file per language) and PaddleOCR on MNN (`core:ocr-mnn`: MNN built from a submodule with its CPU backend, behind a small JNI wrapper). A Paddle recognizer requires a text detector, a model of its own shared by the recognizers of one PP-OCR version; the detector finds lines, each line is cropped along its rotated rectangle and read upright, and a recognizer with right-to-left letters gets its lines put into reading order (`RightToLeft.readingOrder`, the bidirectional algorithm's rules for Arabic text): Latin runs keep their inner digits, spaces and signs; European and Arabic-Indic digits form numbers joined only by `. , : / ٫ ٬` between two digits; other signs stand apart, and brackets and guillemets outside Latin runs are mirrored. A detector's archive may carry its post-processing thresholds (`detector.properties`). MNN keeps the memory of the largest input a network has run on (about 350 MB after a whole screen); ten seconds after the last recognition the engine sizes its networks for small inputs and frees it, keeping the models loaded, so quick rescans do not take it again. The user chooses the model per language (ML Kit where it reads the script, or an installed catalog model); without a choice the language uses ML Kit where it reads the script, else its recommended model once installed, else the best installed one. A scan holds the models it reads with (`OcrModelStore.hold`): deleting a held model only marks its directory, which goes when the last hold is released or at the next start. The manifest records each file's size and SHA-256; a model whose file is missing or of another size, or whose files fail the hash after an engine error, counts as damaged, is left out of the selection and is listed on the start screen. "Check for updates" compares the installed models' versions with the catalog's. Tesseract gives Thai cluster by cluster: the clusters are joined without a separator, and with a space where the gap between two is wider than 0.4 of the line height (`LanguageSupport.ocrSpaceGap`, measured on screens: spaces 0.28-0.74, gaps inside words up to 0.37). Khmer it gives phrase by phrase, which take a space where the gap is wider than 0.15 of the line height. Every engine's words pass through the language's support class, which writes Latin look-alikes in Cyrillic words as Cyrillic letters (in Serbian only on lines that are mostly Cyrillic, there also in words of look-alikes alone, except Latin words in capitals outside a heading in capitals) and letters a language never writes as the one they stand for (Swedish ả and â as å, Norwegian and Danish ä as well), one character for one. Text read from apps does not pass through it.

The interface language is separate: string resources in 14 locales, chosen in Appearance or in the system's app language settings (Android 13 and newer). The system applies a per-app language to activities only, so the application object and the accessibility service return resources in that language themselves (`AppLanguageResources`); the bubble, popup, crop editor and notifications follow it.

## Privacy

Imports, deletions, resets, update checks and the bundled install log each step with ids, sizes, timings and dictionary titles, so a shared log shows where one went wrong. Logs never contain recognized text, looked-up words, note contents or URLs with terms: exceptions are logged through `redacted()`, which keeps the type and stack but drops messages, and URLs through `redactUrl()`. Every module logs through `core.common.log.Log`, which writes each line to logcat and to the app's own log file (`LogFile`, installed by `AppLogs` first thing in `Application.onCreate`): logcat keeps an app's lines for minutes at most and some phones show an app none of them. The file lives in `noBackupFilesDir/logs` (out of backups, removed with the app), holds at most two files of 4 MB, is written in call order on one background thread, and gets uncaught exceptions (redacted) before the process ends. Each process start logs the version and how earlier processes ended (`ApplicationExitInfo`: force-stop, crash, low memory and so on). Sharing or saving the log writes one file: the version and device, the own log, then what logcat still holds for the app (library and system lines the own log lacks). When the accessibility service stops, it logs whether it is still on the enabled list (still there: the system unbound it; gone: the switch was turned off), the time since the last bubble touch and scan, and the windows that opened or came to the front in the last 10 s (package names of system and phone-maker apps only), then checks the list again 3 s later; a notification with a button to the accessibility settings tells the user the bubble is gone. A scan logs its stages with timings (capture, app text, cloud request, on-device bands, draft and final), and events such as docking, note results and audio lookups are logged as outcomes and counts, never per aim movement. Translations log the service, the time and the error kind, never the sentence or its translation; the sentence itself goes only to the translation services, and only when the translation button is tapped or a note's template has `{sentence-translation}`. Photos and their recognized text stay in `noBackupFilesDir/photos` (out of backups); the photo store logs ids, sizes and orientation, never paths or text.

## Threading

- The overlay runs on the main thread of the accessibility service; OCR, lookups and file work suspend on IO or Default dispatchers.
- The hoshidicts session is used from one coroutine at a time (a mutex in `HoshidictsEngine`); imports do not touch the session and run in parallel with lookups.
- `DictionaryRepository.withLookup(language)` holds the registry mutex from loading a language's dictionaries through its queries, including glossary image reads, so another language's lookup, CSS read or registry change cannot replace them mid-query. A note keeps the language captured when adding it, including its sentence parsing and glossary images.
- Search results carry their language. Switching the active language closes the previous note session before rendering matching results, clearing note IDs, selected audio and automatic playback state. The short-lived Anki status cache is keyed by language and rejects stale answers after a session closes.
- Home, Search and the overlay share `LanguageInstallation`: enabled dictionaries with complete files, mandatory catalog categories, installed model versions and the configured recognition mode determine readiness. Catalog downloads keep language and entry IDs in WorkManager tags so changing progress names does not lose their scope. A blocked scan opens status before app-text reads or screenshot capture; Search observes readiness and reruns when dictionaries arrive.
- The lookup page talks to Kotlin through `@JavascriptInterface` methods, which post to the main thread.
- The popup's WebView renderer runs at a priority the system may lower while the popup is hidden (`setRendererPriorityPolicy(…, waivedWhenNotVisible = true)`); if the renderer is reclaimed, the page is recreated at the next scan once its recognition runs on its workers, since creating it holds up the main thread for most of a second. The search screen's embedded page keeps the default priority.
- A cancelled ML Kit task cannot be stopped, so the on-device pass works on its own copy of the screenshot and frees it when the task ends.
- Recognition is collected on the main thread, so the engines move their heavy work off it: screenshot copies and crops, ML Kit's line building and the cloud engine's image encoding on Default, the cloud request and its response on IO. Screenshot callbacks copy the image on a background executor.
- The scan's screenshot is shared by the scan, its recognition, its small-text bands and a note being added, whose crop editor draws it (`SharedScreenshot`): each user retains it and releases it when done, and the last one frees it. A note releases it as soon as the editor returns its crop. Closing the scan (docking, rotation, hiding the bubble) closes an open crop editor as cancelled; a note already being added goes on, but a picture is no longer taken for it.
- Values derived from the installed dictionaries (styles, tag descriptions, frequency modes, transcription tags) are kept until the registry changes (`DictionaryRepository.generation`).
