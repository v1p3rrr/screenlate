# Architecture

## Modules

```
app ──────────────┬──> overlay ──┬──> core:ocr ──> core:common
                  │              ├──> core:anki ─> core:common
                  │              ├──> core:translate ──> core:common
                  │              └──> dictionary:api ──> core:common
                  ├──> dictionary:engine-hoshidicts ──> dictionary:api   (hoshidicts, QuickJS-ng)
                  └──> dictionary:render-yomitan (assets only)
```

| Module | Contents |
|---|---|
| `app` | Application (Hilt, WorkManager factory), Compose screens: home with setup warnings, search, one Settings screen leading to bubble, lookup, dictionaries, Anki and audio, popup, translation (`translate/`), appearance (theme, e-ink mode, language, popup font and CSS), backup and restore (`backup/`) with the Yomitan import as its last card (`yomitan/`), background work and About; OCR test. The Languages screen, the first run and a language's download screen (`languages/`). The dialog about what the accessibility service reads and sends comes before its settings open until the user agrees (`home/AccessibilityDisclosure`). `ProcessTextActivity` for the text selection menu. |
| `overlay` | Accessibility service, bubble state machine (`OverlayController`), window screenshots, app text from the accessibility tree, the lookup page (`web/LookupPage`, `assets/popup/`), popup placement, crop editor, Anki buttons (`anki/PopupNotes`), page fonts and custom CSS (`fonts/`), Quick Settings tile (holding it opens the app through `BubbleTileSettingsActivity`), the optional keep-alive foreground service (`BubbleKeepAliveService`), the service's running state for the start screen (`OverlayServiceStatus`), whether the active language is ready to scan (`install/LanguageInstallation`), round flags for languages (`ui/Flags`). |
| `core:common` | `Language` and `LanguageSupport` (everything language-specific: lookup start, spelling variants, romaji, sentence rules, fonts, audio defaults), `MappedText`, the Simplified and Traditional Chinese character table, geometry, app settings, language profiles (`LanguageProfiles`: turned-on, active and starred languages), shared OkHttp client, local network address checks, log redaction. |
| `core:ocr` | `OcrEngine` with a cloud engine (hand-written protobuf) and the device (`DeviceOcr`: ML Kit, or an engine with downloaded models from `OcrModelStore`: Tesseract, PaddleOCR), `CompositeOcr` (draft, then final), `TextLayout` for hit testing. |
| `core:ocr-mnn` | MNN (submodule, CPU backend) and its JNI wrapper `MnnNetwork`, which runs the PaddleOCR models. |
| `core:anki` | AnkiDroid API wrapper behind `AnkiBackend`, note settings, field templates, sentence extraction, setup status, audio sources and playback. |
| `core:translate` | `SentenceTranslator` over the Bing, Google and Edge translators (`Translator`), the language table (generated by `scripts/translation/languages.py`), translation settings. |
| `dictionary:api` | `DictionaryEngine` interface and lookup models, registry (Room), import queue (WorkManager), bundled dictionaries, download catalog (formats 1 and 2), update check, `YomitanSorter`, Yomitan collection export converter, the files written next to a dictionary at import (tag notes, transcription tags, reading index), form-of tag names, the wordfreq frequency dictionary builder. |
| `dictionary:engine-hoshidicts` | `DictionaryEngine` on top of hoshidicts (C++, JNI); for languages other than Japanese, Yomitan's language code in QuickJS (bundles in `assets/yomitan-language`) and the form-of table. GPL-3.0. |
| `dictionary:render-yomitan` | JavaScript and CSS that render Yomitan structured content, images, furigana and pitch accent. GPL-3.0. |

The two GPL modules implement interfaces or asset contracts defined elsewhere, so they can be replaced without touching the rest.

## From the bubble to a dictionary entry

1. **Scan.** Pulling the bubble out of the dock (or tapping it) takes a screenshot of the app window under the overlays (`takeScreenshotOfWindow`, API 34+; older versions capture the display with the overlays hidden for a frame), so the popup is never recognized and the text under it is. With "Read app text", `AccessibilityText` reads the application windows' accessibility tree while the screen is captured, and OCR runs as well. Neither waits for the other: whichever is ready is shown, and app text takes precedence where both have text, with OCR adding only the lines app text lacks. "App text only" skips the screenshot and OCR (the screenshot is taken later only when a note asks for a picture). Nodes whose character boxes cannot be trusted are left to OCR: the same box for every character (a WebView reporting the node's bounds) and text fields whose first box sits at the field's corner (Compose fields, whose boxes include the padding). A combining mark typed apart (a stress or tone mark), which a text view gives an empty box, stays with its letter.
2. **OCR.** `CompositeOcr` runs ML Kit on the device and the cloud engine in parallel. ML Kit first reads a band of the screen around the aim (`FocusBand`, again when the aim has moved out of it), then the whole screen; each result is shown as a draft until the cloud result replaces it. ML Kit's time grows with the amount of text, so the band is ready several times sooner than the whole screen. The model is loaded when the bubble starts and again when another model takes over (chosen in the settings, installed or deleted). The cloud engine gets a JPEG of at most 1500 px; its coordinates are normalized to the image and mapped back to the screen. A touch on the bubble opens the connection to the cloud host with a request that carries no screen content, unless the host was contacted in the last 30 s, so the first scan after a pause does not wait for the handshake; the scan's request waits up to 3 s for a connection being opened. `OcrOptions` can limit a scan to one engine or defer ML Kit's whole-screen pass until the cloud engine is 3 s late or fails (`deferWholeImage`). ML Kit's symbol boxes sometimes lag behind the glyphs by up to half a character; `SymbolLag` moves the inner boundaries of such words onto the gaps between glyphs when the pixels clearly show them.
3. **Hit test.** `TextLayout` splits every recognized word into characters (per-character boxes when the engine has them, otherwise even splits along the reading direction) and finds the character under the aim point. The text from that character to the end of its paragraph, up to the scan length (16 characters by default), is the lookup text; in a language written with spaces it starts at the beginning of the word under the aim. Words, and the lines of a paragraph, are joined by each word's separator (none in Japanese), so a phrase broken across lines is still found. Cloud recognition gives no separator after a word hyphenated at a line end; `withHyphenBreaks` puts the language's separator there, so the lookup sees the break. `ReadingOrder` puts paragraphs into reading order first: vertical columns right to left, and a column that runs to the bottom of its text joined with the column that goes on from it, so a word broken at a line or column end is read as a whole.
4. **Lookup.** `DictionaryLookup` loads the enabled dictionaries into the engine on first use. hoshidicts deinflects every prefix of the lookup text, groups results by expression and reading, and sorts them. In Japanese, form-of entries (a glossary item `["lemma", ["tag", …]]`, as in Wiktionary's rows of inflected forms and spellings) are then followed one step, as Yomitan does: the items leave the definitions, an entry left without definitions is dropped, and the lemma's entries join the results with the item's tags added to the rule chain, unless the same word is already found as well or better (`form_of.cpp` in the engine module). `YomitanSorter` applies Yomitan's full order including dictionary priority. The language's spelling variants (`LanguageSupport.spellingVariants`) and, when enabled, romaji converted to kana are looked up as well; `MappedText` maps their matched lengths back to the screen text. In a language written with spaces they include a word hyphenated at a line end, joined and with its hyphen kept. Other languages go through Yomitan's own language code: a bundle per language (`assets/yomitan-language`, built by `scripts/yomitan-language`) runs in QuickJS inside the engine library and turns the text into candidates with the language's text processors (such as decapitalizing) and deinflection rules, and hoshidicts answers exact queries for them. Form-of entries (a form pointing to its lemma, which Wiktionary dictionaries hold by the million) are split out of an archive at import into a compact table next to the dictionary, memory-mapped for lookups; a candidate found there leads to its lemma, filtered by part of speech as in Yomitan, and the form's tags show as its rule chain. One exception to that filter: an English entry without a part of speech matches a verb form of a phrase whose second word is an adverb particle ("picked up" → "pick up"); the bundle's glue marks such candidates, and the interposed-object rule stays typed only. A language that writes the syllables of a word apart (Vietnamese) starts the lookup at the one and two words before the aimed one as well (`LanguageSupport.earlierStartOffset`): `DictionaryLookup` keeps from those starts only words that reach the aimed one and puts them first (`fromEarlierStarts`), and each result's `start` tells the overlay where its word begins on screen. Every language written with spaces starts the lookup at the first half of a word hyphenated at a line end as well when the aim is on its second half. Results reached only through form-of entries with a tag the language ignores (`LanguageSupport.ignoredFormTags`: Vietnamese `classifier`) are dropped. The same word (expression and reading, compared as the language's Yomitan reading normalizer does: pinyin without spaces or apostrophes) from several dictionaries or spellings becomes one result in the place of the first. A language written in two scripts (Chinese) tags each result with its script (`lang`, which picks the glyph forms on the page): the word's own, else the text's, else the one chosen on the Languages screen; `ChineseScripts` decides by the characters only one script uses and converts text character by character, from a table that `scripts/chinese-scripts/build.py` generates from Unihan and CC-CEDICT. A form-of entry that only spells its lemma in the other script (Wiktionary's `Simplified-Chinese`) shows the spelling that was read, so it merges with dictionaries that list that spelling; with one script fixed, the text is also looked up converted, and a word gives way to its spelling in that script. A typed search in a language with a reading search (Chinese pinyin, `LanguageSupport.readingKey`) also finds words by their reading: at import, `ReadingIndexBanks` writes a `ReadingIndex` next to the dictionary, a memory-mapped file of the words of each toneless key, the likely common ones first (a character that more of the dictionary's words contain counts as more common); `DictionaryLookup.lookupQuery` looks up the first 80 words of the query's key in the chosen script, keeps those whose reading has the key, and ranks the tones and apostrophes typed (`readingMatch`) before Yomitan's order. Characters of the matched word that a character dictionary describes (Japanese kanji, Korean hanja; `LanguageSupport.singleCharacterEntries`) follow the results as entries of their own, and a text that matches no term shows the entry of its first character (`characterEntry`), with the dictionary's tags for it (jouyou, basic hanja for education).
5. **Render.** The overlay sends the results as JSON to the lookup page in a pre-warmed WebView. The page builds the cards; glossaries go through `YomitanRender` (structured content, images served from the engine, each dictionary's `styles.css` scoped to its own entries). `&quot;` and `&apos;` that a dictionary's packaging left in plain text show as quote marks. Headwords get their reading as ruby: Japanese through `YomitanRender.furigana`, languages with a syllable per character through `HeadwordReading` (`reading-zh.js` splits pinyin into syllables with their tones, one above each character where they match up); a Russian reading that only adds stress marks takes the word's place (`reading-ru.js`). `overlay/fonts` supplies the page's `lang`, the phone's font for the language declared by its local name and limited to the script, downloaded or added fonts (limited to the script unless chosen for all text), and the user's CSS, applied last with the page's font list appended to each `font-family`. The page's content security policy lets only stylesheets and fonts come from the internet; scripts, images, media and requests stay on the page's own host.
6. **Highlight and placement.** The matched length of the first result decides how many characters are highlighted. `PopupPlacement` puts the popup above the word, else below the bubble, in landscape beside them on the side with more space (shrinking a little); when that does not fit, the popup keeps its size at the screen's edge on the roomier side and covers part of the word or the bubble rather than getting low or narrow.

Aiming again only repeats steps 3–6; the screen is not scanned again until the bubble goes back to the dock or is tapped.

## Anki export

The page builds the dictionary markers of an entry (glossary HTML with scoped CSS, furigana, pitch, frequencies) because it already has the renderer. Glossary HTML comes from the renderer's tag allow-list with escaped text; each dictionary's scoped CSS goes into a `<style>` element with any `</style` written as `<\/style`, so a dictionary cannot end the element and add markup to the card. `PopupNotes` adds the sentence and cloze markers from the OCR paragraph, the audio clip and, on a long press, the cropped screenshot. The sentence and the crop frame come from the view shown when ➕ is pressed (`NoteSource`); until the scan's final result ➕ is grey and only explains itself (`noteWaitsForText`, the page state's `noteWait`), except for a word from the app's own text; a new scan closes the previous popup; a note that finishes after its scan closed stays out of the next scan (`ScanNotes`); `AnkiNotes` renders the field templates, handles duplicates and talks to AnkiDroid through its content provider; its `check(language)` asks AnkiDroid about each part of a language's setup for the Anki page's connection check, read-only. A newly chosen note type gets its templates from `FieldTemplate.guess`: a `NoteTypePresets` entry when the note type's name and fields match a well-known mining note type (its authors' templates, with this app's nearest marker where they use their own), otherwise Yomitan's rule of whole field names with aliases, the note language's own field names first (`LanguageSupport.ankiFieldNames`: Pinyin, Traditional). A language written in several scripts has a marker for the word in each (`LanguageSupport.scriptMarkers`), which `PopupNotes` fills through `DictionaryLookup.inScript`: the character table's conversions, the first one a dictionary lists with the word's reading. Furigana of a language with a syllable per character use the same `HeadwordReading` rules as the headwords; Russian stress marks go into the word, in a sentence only into words written in their dictionary form (`HeadwordReading.sentenceSegments`). The + menu offers the furigana markers only where `LanguageSupport.furiganaMarkers` is set (Japanese, Chinese, Russian). Media files go to AnkiDroid through a FileProvider.

## Sentence translation

`core:translate` talks to three keyless services: Bing (a key read from the translator's web page, kept for its lifetime and fetched again when the service refuses it), Google's `gtx` endpoint and the translator built into Edge (Microsoft's language codes, no key). Each `Translator` knows its language codes and longest text. `SentenceTranslator` runs the services in the user's order and moves to the next one when a service fails or gives no answer within 3 s; it reports either the text with its service or every service's `TranslationError` (a kind; for HTTP errors the status; for the logs a detail without text, such as an unexpected answer's shape). A certificate that is not valid at the device's date has its own kind, so the user is asked to check the clock. A request runs in the translator's own scope: callers asking for the same text share it, and a success is kept for 10 minutes (16 entries), so a note gets the translation the popup shows. The target is the chosen language or the interface language (`TranslationLanguages.defaultFor`, English when it is the source language).

In the overlay, `SentenceTranslation` connects it to the page and to notes. The translation button on the page calls `onTranslate` with a request number; the controller translates the first view's sentence (the same one a note would take) and answers with `showTranslation` (the text, its service and the sentence for the copy button), which the page ignores when it no longer shows that request. The page state carries the view's sentence: a new scan result shown while the popup stays open (`render` with `continued`) keeps the translation when the word and the sentence are the same, and anything else drops it. `PopupNotes` asks `SentenceTranslation.forNote` when ➕ is tapped, so the request runs while a crop editor is open, and fills `{sentence-translation}` once the note is ready, waiting up to 5 s more and leaving the field empty otherwise. The settings page's test calls each service separately with a 15 s limit and keeps nothing.

## Dictionaries

`DictionaryRepository` is the only writer of the registry. Imports (bundled archives, files, downloads, Yomitan collection exports) run as foreground WorkManager jobs: the archive is converted into a staging directory, moved into `files/dictionaries/<uuid>/`, registered, and the engine is reloaded. The jobs run on two unique chains (`DictionaryImports.QUEUES`, `APPEND_OR_REPLACE`), a new job going to the chain with fewer unfinished jobs, so a download that stalls holds up only its own chain; each chain's job has its own notification. The import steps (the engine's import of an archive, a model install, a whole file, collection or bundled install) take a process-wide mutex (`DictionaryImports.importing`), as the native importer needs a lot of memory: a job waiting for it shows as waiting, and a death of the process meanwhile does not count against it. Queueing runs under another mutex and awaits WorkManager, so the next job queued sees the previous one: `download` and `downloadModel` first look for a job tagged with the same catalog entry or URL and return an unfinished one, or resume a stopped one that is still listed. The engine keeps neither tag descriptions nor the tags of phonetic transcriptions, so the import reads them from the archive into files next to the engine's (`TagBanks`, `TranscriptionTagBanks`): the transcription tags are kept by a 64-bit hash of term and transcription, sorted for a binary search. A lookup turns them into regions (`TranscriptionRegions`: flag emoji, and accent names per language) and cleans the list up (`Transcriptions`); the page orders the transcriptions by the user's audio regions. A catalog entry that names a `build` (a wordfreq word list) is downloaded like an archive, checked against its SHA-256 and converted into a dictionary archive (`WordfreqDictionary`; a language written in two scripts also gets each word's spellings in the other one with its rank, as wordfreq writes Chinese in Simplified characters only) before the import; the frequency dictionary then sorts its language's results unless another one was chosen (`DictionaryRepository.preferSortDictionary`). A dictionary with the same title, or the one an update was started for, is replaced in place. A failed import is reported on its task and does not stop the imports queued after it. Before the engine imports an archive, its title is checked: the engine writes into a directory named after it. An import the process died in is run again by WorkManager, from the start, once: a job whose `runAttemptCount` shows two earlier runs ends with an "interrupted" result instead, so an archive that kills the process cannot loop. As every app start queues the bundled install again, an interrupted bundled install also pauses it until the app's install time changes (an update); the task's "Try again" and a dictionary reset end the pause. "Cancel" on one task stores its id in the preferences (the process may die before the job ends) and cancels the job's body, which runs inside `CancellableRuns`, without cancelling the WorkManager job: a cancelled job ends successfully, so the jobs queued after it still run (cancelling it in WorkManager would cancel them too). Downloads and collection conversions check for the cancel between reads; the import notification's Cancel action goes through the same path (`ImportCancelReceiver`). A download job has a network constraint; it writes into an archive named in its input, so a later run continues it (`ResumableDownload`: a range request with If-Range on the first response's strong ETag or Last-Modified; a state file next to the archive keeps that validator and whether the download finished, so a run after a death during the import does not download again). A download that breaks off (the read timeout is 20 s) queues a copy of its job at the end of a chain (`DictionaryImports.requeue`: the same input and archive, its retry number in the input and a tag, an initial delay of 30 s doubled with each retry) and ends with a "requeued" result, which the task list leaves out; a copy queued while the job was cancelled or stopped by WorkManager is cancelled again at once. After three retries, as after an HTTP 4xx or a failed import, the job ends with a resumable result that carries its input, and `DictionaryImports.resume` queues it again. Runs that die while downloading or waiting for the import mutex are counted like system stops, so only deaths during the import count towards the two runs. Finished tasks are dismissed one by one (their ids are kept in the preferences until WorkManager prunes the job); dismissing a stopped download deletes its partial archive; the engine's import of an archive runs to its end, and the repository checks again before it registers the result. A cancelled or given-up job deletes the copy of the picked file it was to read and gives back the kept access to it. Each job is tagged with the name of the archive it reads, and the first import job of a process removes what earlier processes left: directories of no registered dictionary, staging directories, and downloaded or copied archives (with their state files) that no unfinished job or stopped download reads (when an unfinished job from an older version has no such tag, only archives older than six hours). Orphaned directories are listed under the registry lock, so the list never holds a dictionary between its move and its registration, and deleted after it, so lookups do not wait for large deletions.

A Yomitan collection export is one JSON file with the rows of all dictionaries, table by table. `YomitanBackup` reads it twice as UTF-8 bytes without decoding row values: first to measure the chosen dictionaries (`measure`), then to copy their rows into one Yomitan archive per dictionary (`convert`). `CollectionSpace` turns the measurement into the peak storage of the import (all archives exist before the first one is imported, each is deleted after its dictionary is installed) and decides whether the archives are stored uncompressed (fastest), deflated (when only that fits), or not written at all (the task fails with the needed and free space).

`DictionaryReset` returns the dictionaries to a fresh install. No screen starts it any more (the Dictionaries screen has no reset); it finishes a reset that an earlier version left interrupted. It cancels the import jobs by tag and waits until no worker is inside its body (`DictionaryImports.cancelAll` counts them), forgets the bundled installs, deletes every dictionary through `DictionaryRepository.deleteAll`, and queues the bundled archives again. Before it deletes anything it stores the number of the run in the preferences and removes it once the bundled archives are queued; `resumeInterrupted`, called at app start, runs the reset once more after a first run the process died in, and after a second one gives up and stores a flag. The start screen shows that flag once in a dialog, and the Dictionaries screen as a card until it is closed or a reset succeeds. The queued install continues as any import does. A reset that fails with an exception is reported on the Dictionaries screen and not run again by itself. `phase` (deleting, then installing until that import job finishes) drives the spinner at the top of the Dictionaries screen.

## Settings reset

All settings live in one preferences DataStore. Its provider keeps the settings as last read (`SnapshotDataStore`), and every repository offers a `cached` value from it, so a screen's first frame shows the user's values rather than defaults that change a moment later; reads and writes still go through the DataStore. Data from outside the settings is kept the same way while the app runs: AnkiDroid's last answer (the Anki screen shows it dimmed and without taps until AnkiDroid answers again, `Modifier.pending`), the Dictionaries screen's last state, the dictionary list, the launcher apps and the popup's typefaces. `SettingsReset` removes stored keys rather than writing defaults; `SettingsKeys` maps key names to the settings page that resets them (the global reset also clears update announcements and one-time hints). Dictionary bookkeeping, migrations and the interface language (kept by Android) are never touched. Leaving e-ink mode goes through `EInkSizes.restore`, and the Background page's reset also stops the keep-alive service. The popup CSS editor saves after a pause, so its reset first replaces the pending text with the default; text fields that keep their own copy (the Anki tags) take the new value once they lose focus, and confirming a reset clears focus.

## Backup and restore

`app/backup` writes one zip: a manifest (format version, app version, the sections it holds, its languages and recognition models) first, then the preferences of the chosen sections as typed JSON (`BackupPreferences`: key prefixes decide the section; internal state such as one-time hints is left out), the dictionary list (registry entries without ids, matched by title on restore, each with the size of its files), the chosen popup fonts (`fonts/fonts.json` and their files, `FontBackup`), the files of each recognition model (`models/<id>/`, which versions before them skip), and each chosen dictionary's converted directory. The choice is a set of sections plus, for languages, fonts and dictionaries, `FileChoice`: the item's mark and the files marked otherwise, so a file added later takes the item's mark; `BackupChoiceStore` keeps the last choice in preferences outside the backup. A language left out takes out its own preference keys (`SettingsKeys.languageOf`), its dictionaries (by source language) and sort dictionary, the catalog fonts of its language and the models no chosen language uses; dictionaries without a language and the user's own fonts are shared. Japanese's audio key also holds the volume and autoplay every language shares, so without Japanese only those two values go in and come back (`SharedAudioSettings`). The turned-on languages stay in the General section, limited to the chosen ones; restoring General adds the chosen languages to the turned-on ones and takes the backup's active language, stars and flags only for them (`BackupLanguages.merged`), so no language is turned off. A backup of an older version has no language list: its turned-on languages (Japanese alone without them) and the languages of its dictionaries and fonts stand for it. Opening a backup reads its head up to the first model or dictionary file, which lists the fonts with their sizes, also in older backups whose fonts belong to the popup section. Restoring reads the zip as a stream: checked preference sections are replaced in one DataStore edit for the shared keys and the chosen languages' own, the chosen fonts, models and dictionaries are staged and handed to `PopupFonts.restore` (merged into the installed fonts by id, files no font uses are deleted), `OcrModelStore.restore` (skipped when the same version is installed) and `DictionaryRepository.restore` (a dictionary with the same title is replaced in place and keeps its id, switch and priority), and the dictionary list entries of the chosen languages are applied last to whatever is installed. `BackupManager` is a singleton with its own scope, so the work goes on when the screen is left.

## Updates and releases

`update/AppUpdates` reads the latest stable GitHub release, picks the APK for the device's ABI, checks that it is a newer Screenlate signed with the same certificates and installs it through `PackageInstaller` (`UpdateReceiver` gets the session status). The version comes from git tags: `vX.Y.Z` gives the name X.Y.Z and the code X·10000 + Y·100 + Z (`build-logic`'s `ScreenlateVersion`). CI (`.github/workflows`) builds and tests every push, and a tag builds per-ABI and universal APKs, a source archive with submodules and a changelog for the GitHub Release.

## Languages

Language is a parameter of OCR, lookup and rendering (`core.common.Language`). Whatever differs between languages lives behind `LanguageSupport`; Japanese, English, Chinese and Korean are implemented so far.

`LanguageProfiles` (`core:common`) keeps the turned-on languages, the active one, up to two starred quick languages and the chosen flag countries in the preferences; activating a language moves the stars in the same write (a starred language swaps roles with the active one, any other takes its star). Each language support class lists its flag countries; `Flags` (`overlay`) maps them to the round flag drawables that `scripts/flags/circle_flags.py` generates from circle-flags, used by the bubble menu and the app. Settings kept per language use their old key for Japanese and the key with `_<code>` for other languages. The application settles the first run before anything writes preferences: any stored preference or installed dictionary means an upgrade, which keeps Japanese on and, in the same write, keeps the translation button on unless it was turned off (it is off by default on new installs; a restored backup without the button does the same); a fresh install opens `FirstRunScreen` first. Its result and the check behind "Turn on" on the Languages screen reach the screen as one-shot events from the view model, so a screen recreated meanwhile still navigates. `LanguageSwitch` (`app`) turns a language on, queueing the downloads chosen on `LanguageSetupScreen` as ordinary imports, and off, optionally deleting its dictionaries and models and cancelling their unfinished downloads. The APK carries no bundled dictionaries: Japanese gets its dictionaries from the catalog like any language. `BundledDictionaries` remains for installs from versions that shipped them (Japanese, installed only while Japanese is on); their copies stay, and when their files are missing the start screen offers the catalog download. A catalog entry can also name an archive the app carries (`asset:///`, the Korean hanja dictionary built by `scripts/hanja` from Unihan): it is chosen on the setup screen like a download, but the import copies it from the APK without a network constraint, and the download total leaves it out. A dictionary belongs to its source language, which an import takes from the matching catalog entry first, then from index.json (where Wiktionary's `all` names no language), then from the replaced dictionary, then from the archive's content. The start screen reports, per turned-on language, the mandatory catalog categories that no enabled dictionary covers, with the progress of the queued imports.

On-device recognition: ML Kit's Latin, Japanese, Chinese and Korean models are bundled; each script gets its own recognizer (Latin-script languages the Latin one, which is as accurate as the Japanese model on Latin text and twice as fast). A script without an ML Kit model needs a `ModelOcrEngine`, whose code is in the APK and whose models are catalog entries of the category `OCR_MODEL`: the import worker downloads them like dictionaries and hands them to `OcrModelStore`, which installs a file only when its SHA-256 matches the pinned one, unpacks zip archives, keeps a version per model and replaces an older one. Several languages may share a model (a text detector); turning a language off deletes only the models no other turned-on language uses. `DeviceOcr` asks ML Kit first, then the engines whose installed models read the language; a language the device cannot read goes to the cloud alone, and a device-only scan of it fails with a message. Lines carry their direction: a horizontal line whose first strong character is right-to-left is split into characters from its right edge.

Engines with downloaded models: Tesseract (Tesseract4Android, one traineddata file per language) and PaddleOCR on MNN (`core:ocr-mnn`: MNN built from a submodule with its CPU backend, behind a small JNI wrapper). A Paddle recognizer requires a text detector, a model of its own shared by the recognizers of one PP-OCR version; the detector finds lines, each line is cropped along its rotated rectangle and read upright, and a recognizer with right-to-left letters gets its lines put into reading order. A detector's archive may carry its post-processing thresholds (`detector.properties`). MNN keeps the memory of the largest input a network has run on (about 350 MB after a whole screen); ten seconds after the last recognition the engine sizes its networks for small inputs and frees it, keeping the models loaded, so quick rescans do not take it again. The user chooses the model per language (ML Kit where it reads the script, or an installed catalog model); without a choice the language uses ML Kit where it reads the script, else its recommended model once installed, else the best installed one. A scan holds the models it reads with (`OcrModelStore.hold`): deleting a held model only marks its directory, which goes when the last hold is released or at the next start. The manifest records each file's size and SHA-256; a model whose file is missing or of another size, or whose files fail the hash after an engine error, counts as damaged, is left out of the selection and is listed on the start screen. "Check for updates" compares the installed models' versions with the catalog's. Every engine's words pass through the language's support class, which writes Latin look-alikes in Cyrillic words as Cyrillic letters.

The interface language is separate: string resources in 14 locales, chosen in Appearance or in the system's app language settings (Android 13 and newer). The system applies a per-app language to activities only, so the application object and the accessibility service return resources in that language themselves (`AppLanguageResources`); the bubble, popup, crop editor and notifications follow it.

## Privacy

Imports, deletions, resets, update checks and the bundled install log each step with ids, sizes, timings and dictionary titles, so a shared log shows where one went wrong. Logs never contain recognized text, looked-up words, note contents or URLs with terms: exceptions are logged through `redacted()`, which keeps the type and stack but drops messages, and URLs through `redactUrl()`. The app logs only to logcat, the system's fixed-size ring buffer, so nothing piles up on the device; files are written only when the user shares or saves the log. A scan logs its stages with timings (capture, app text, cloud request, on-device bands, draft and final), and events such as docking, note results and audio lookups are logged as outcomes and counts, never per aim movement. Translations log the service, the time and the error kind, never the sentence or its translation; the sentence itself goes only to the translation services, and only when the translation button is tapped or a note's template has `{sentence-translation}`.

## Threading

- The overlay runs on the main thread of the accessibility service; OCR, lookups and file work suspend on IO or Default dispatchers.
- The hoshidicts session is used from one coroutine at a time (a mutex in `HoshidictsEngine`); imports do not touch the session and run in parallel with lookups.
- `DictionaryRepository.withLookup(language)` holds the registry mutex from loading a language's dictionaries through its queries, including glossary image reads, so another language's lookup, CSS read or registry change cannot replace them mid-query. A note keeps the language captured when adding it, including its sentence parsing and glossary images.
- Search results carry their language. Switching the active language closes the previous note session before rendering matching results, clearing note IDs, selected audio and automatic playback state. The short-lived Anki status cache is keyed by language and rejects stale answers after a session closes.
- Home, Search and the overlay share `LanguageInstallation`: enabled dictionaries with complete files, mandatory catalog categories, installed model versions and the configured recognition mode determine readiness. Catalog downloads keep language and entry IDs in WorkManager tags so changing progress names does not lose their scope. A blocked scan opens status before app-text reads or screenshot capture; Search observes readiness and reruns when dictionaries arrive.
- The lookup page talks to Kotlin through `@JavascriptInterface` methods, which post to the main thread.
- The popup's WebView renderer runs at a priority the system may lower while the popup is hidden (`setRendererPriorityPolicy(…, waivedWhenNotVisible = true)`); if the renderer is reclaimed, the page is recreated at the next scan once its recognition runs on its workers, since creating it holds up the main thread for most of a second. The search screen's embedded page keeps the default priority.
- A cancelled ML Kit task cannot be stopped, so the on-device pass works on its own copy of the screenshot and frees it when the task ends.
- Recognition is collected on the main thread, so the engines move their heavy work off it: screenshot copies and crops, ML Kit's line building and the cloud engine's image encoding on Default, the cloud request and its response on IO. Screenshot callbacks copy the image on a background executor.
- The scan's screenshot is shared by the scan, its recognition, its small-text bands and a note being added, whose crop editor draws it (`SharedScreenshot`): each user retains it and releases it when done, and the last one frees it. A note releases it as soon as the editor returns its crop. Closing the scan (docking, rotation, hiding the bubble) closes an open crop editor as cancelled; a note already being added goes on, but a picture is no longer taken for it.
- Values derived from the installed dictionaries (styles, tag descriptions, frequency modes, transcription tags) are kept until the registry changes (`DictionaryRepository.generation`).
