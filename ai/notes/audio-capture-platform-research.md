# Playback audio mining: preliminary platform research

Checked against official Android documentation on 2026-10-16. Research only; the proposals below are not approved product decisions or an implementation plan.

## Feasibility and hard limits

Android 10/API 29 introduced `AudioPlaybackCapture`: `AudioRecord` reads another app's playback when configured with `AudioPlaybackCaptureConfiguration`. It requires runtime `RECORD_AUDIO` permission, user-approved `MediaProjection` consent, and both apps in the same user profile. Only `USAGE_MEDIA`, `USAGE_GAME`, and `USAGE_UNKNOWN` playback with effective `ALLOW_CAPTURE_BY_ALL` is capturable. The source app can opt out; the most restrictive manifest/app/player policy wins. Target API 29+ apps allow capture by default, older apps opt in. Filters can constrain capture to a UID. A revoked projection stops streams, so handle `MediaProjection.Callback.onStop()` rather than continuing to collect silence. These APIs do not promise access to every streaming service or protected title; test the owner's actual players and content before committing to this feature. Do not infer that every DRM title behaves identically. [Capture playback](https://developer.android.com/media/platform/av-capture).

For target API 34+, declare `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_MEDIA_PROJECTION`, and a service with the `mediaProjection` type. Obtain user consent before starting this service; obtain the projection after the foreground service starts. Android 14 also rejects reuse of the consent intent and multiple `createVirtualDisplay()` calls per token: avoid extrapolating screen-capture code that repeatedly recreates virtual displays. A long-lived recording mode should be one explicitly started capture session, with visible system/service status and teardown. This is not a permission-free extension of Screenlate's existing accessibility screenshots. [Projection guide](https://developer.android.com/media/grow/media-projection), [service prerequisites](https://developer.android.com/develop/background-work/services/fgs/service-types#media-projection).

Apps targeting Android 15 cannot start a projection foreground service from `BOOT_COMPLETED`. Start this optional mode through an explicit user action rather than automatic boot recording. [Android 15 FGS changes](https://developer.android.com/about/versions/15/changes/foreground-service-types#media-projection).

## Proposed recording architecture

`AudioRecord` requires regular reads; its small platform input buffer is not the user's rewind history. Add an application-owned bounded PCM ring buffer on a worker thread, identified by frame indexes and monotonic timestamps. Copy the selected history into an immutable draft when starting a note so recording cannot overwrite it. [AudioRecord](https://developer.android.com/reference/android/media/AudioRecord), [capture builder](https://developer.android.com/reference/android/media/AudioRecord.Builder#setAudioPlaybackCaptureConfig(android.media.AudioPlaybackCaptureConfiguration)).

Engineering estimates: 60 seconds of 48 kHz, stereo, 16-bit PCM uses 11.52 MB (about 11 MiB); mono uses half. A waveform can use a downsampled amplitude envelope; encode only the confirmed cut for Anki media. Keep temporary drafts bounded and delete them on cancel/session termination. The project can supply a recorder interface and a separate pure PCM editing layer; neither requires a language-specific implementation or an LLM during use.

Represent further recording as separate segments. Keep the known user-controlled pause between segments outside the edit timeline; this is more dependable than deciding that all quiet audio is unwanted. Optional threshold-based silence trimming should preserve padding and remain reversible in the editor: music, quiet syllables, and meaningful pauses make arbitrary internal silence removal error-prone. These are proposed engineering choices, not Android guarantees.

## Pausing only the foreground player

The repository already resolves the foreground application through `ForegroundWindow` in `ScreenlateAccessibilityService.foregroundAppPackage()`, and sends it to `OverlayController.onForegroundApp()`. Reuse that signal; do not equate the system's highest-priority media session with the visible player. The current manifests show a `specialUse` keepalive service, not an audio projection service.

On Android 15, enumerate platform sessions with `MediaSessionManager.getActiveSessions(notificationListener)` and match `MediaController.getPackageName()` to that foreground package. Access to other apps' active sessions requires an enabled `NotificationListenerService`, unless privileged `MEDIA_CONTENT_CONTROL` is available. Existing accessibility access alone is not the documented authorization. Package-filtered API 37 helpers are unnecessary for this Android 15 design. [Session discovery](https://developer.android.com/reference/android/media/session/MediaSessionManager#getActiveSessions(android.content.ComponentName)), [controller](https://developer.android.com/reference/android/media/session/MediaController).

Check published `PlaybackState` and available actions; send explicit `pause()` / `play()` requests, avoiding a toggle. A player must expose a usable session and honor commands. Multiple sessions in one package, browser tabs, picture-in-picture, and players without sessions prevent a universal guarantee. UID filtering can avoid mixing a separate background music app into the recording, but does not identify a particular browser tab/player inside one UID. [Playback state](https://developer.android.com/reference/android/media/session/PlaybackState), [transport controls](https://developer.android.com/reference/android/media/session/MediaController.TransportControls).

Crucial limit: standard playback callbacks report state, not a universal origin flag identifying a manual press. Therefore the exact requirement "resume only if the user has never touched the player's controls" is not fully observable across apps. Proposed conservative behavior: remember the exact session and whether Screenlate requested and observed its pause, invalidate resume ownership after contradictory state/position/session changes or uncertainty, and offer leave-paused as a setting. A redundant manual pause while already paused may be invisible. Treat this as a disclosed limitation rather than promising perfect intent detection. [Callback contract](https://developer.android.com/reference/android/media/session/MediaController.Callback), [state contract](https://developer.android.com/reference/android/media/session/PlaybackState).

Audio focus manages competition between sound-producing apps; it can duck/fade other playback and is not a targeted remote-pause API. Do not use focus theft as the main foreground-player control mechanism. [Audio focus](https://developer.android.com/media/optimize/audio-focus).

## First experiment before implementation

Use the intended phone and a short list of real video apps to check capture permission/output, session discovery, package matching, pause confirmation and further recording. Capture support and controllability are separate axes: an app may support one and not the other. This compatibility experiment is the largest early risk reducer; no library can remove the Android/source-app restrictions above.
