The review starts only on the owner's explicit command; until then this note is the instruction.

## How to run each review

- One run per functional module, in the order above unless the owner says otherwise; report findings per run before starting the next.
- Read the unit's code in full, then follow each integration path listed for it into the other side's code (callers and callees), including the non-Gradle channels (JS bridge, DataStore keys, Room, side files, WorkManager, intents, JNI, assets, network).
- Check: correctness and edge cases; coroutine/lifecycle/cancellation and threading (see `docs/architecture.md` → Threading); resource leaks (bitmaps, windows, WebViews, files, native memory); error handling and user-facing messages; privacy rules (logs, URLs); the GPL boundary; `Language` as a parameter (no Japanese hard-coding outside Japanese-specific classes; per-language keys and settings kept apart; Japanese behaving as on `main`); UI rules (scroll, wrap, ⓘ); strings present and natural in all 14 locales; tests covering the logic; docs (`docs/*`, README) matching the behavior.
- Findings are ranked by severity with a concrete failure scenario; fixes follow the usual rules (ask the owner about undecided choices, tests for new logic, verify UI on the emulator). Code that `main` also has is fixed on `main` first, then merged into `languages/main`.
